# cadence run — une demande, une session

Depuis le 2026-11-09, `cadence run` remplace `cadence orchestrate` pour faire une demande. Il joue exactement ce que le banc a mesuré gagnant (docs/v2/banc.md), et rien d'autre.

```bash
cadence run "<demande>" [--piece docs/norme.md]… [--lot L12] [--demande-humaine | --registre D-n] [--taille retouche|fonction] [--complet] [--modele opus|fable] [--sans-porte] [--fond]
cadence run --reponse <id> "<texte>"
cadence run --liste [--inactif <minutes>]
cadence run --clore <id>
cadence run --archives
cadence run --purger [--dry-run]
cadence run --help        # ou -h
```

## Aiguillage (10-11)

Le brief complet (v2d, hook de lecture) ne gagne au banc que quand la demande a des références à lire : normes, captures. Sans elles, au banc court du 10-11, Claude seul faisait aussi bien, et plus vite. `cadence run` choisit donc son mode par une règle mécanique :

- **complet** (brief v2d + hook) : une `--piece` est donnée, ou la demande contient un mot de `references.run` dans `cadence.yaml`, ou `--complet` est passé. Les documents de la référence trouvée deviennent des pièces à lire en entier ;
- **léger** (brief de Claude seul, `v2/briefs/bras-A.md`) : sinon. Le worktree, la porte et l'intégration ne changent pas.

```yaml
references:
  run:
    - mots: [sigwx, jet, cb]
      docs: [docs/normes/sigwx.md]
```

La clé `references:` sert aussi `cadence ref` (`references.dir`) : une seule forme, lue par le même code dans les deux commandes (L760, [config](../config.md#references-cadence-ref-and-cadence-run)). L'ancienne forme, une liste directement sous `references:`, est encore lue comme `references.run`, avec une ligne de migration au lancement ; une forme mal formée est refusée avant la création du worktree.

Le modèle, le mode et sa raison s'affichent au lancement (« session Fable en mode leger (…) »). Dans un vrai dépôt, la ligne « Taille » du brief complet, qui ne sert qu'au banc, est retirée : elle casserait un commitlint. Les mots se comparent sans accents ni casse, en mot entier. Un document ou une `--piece` peut être relatif au dépôt, absolu ou sous `~` : une base de connaissance hors du dépôt (par exemple `~/kb/dossiers/<dépôt>-<lot>.md`) se lit comme une pièce.

## Déroulé

1. Ouvre un worktree à côté du dépôt (`../.cadence-run/<projet>-<id>`), sur une branche `cadence/run-<id>`. Les `node_modules` et `.venv` y sont liés en dur. Avec `run.worktreeOutside: true` dans `cadence.yaml`, le worktree va sous `$CADENCE_HOME/run-worktrees/` (voir « Socle de la session » ci-dessous).
2. Lance une seule session, dans le mode choisi par l'aiguillage et sur le modèle choisi (`--modele`, sinon `CADENCE_RUN_MODELE`, sinon Opus). En mode complet : brief `v2/briefs/bras-sequence-v2d.md` et hook « lecture obligatoire ». Les pièces passées par `--piece` doivent être lues en entier avant toute écriture. Le registre des demandes du dépôt (`.cadence/demandes/`) ne garde que les demandes de l'humain (L701) : voir « Registre des demandes » ci-dessous.
3. Si la session pose une question, le run s'arrête à l'état `attente`. `--reponse` reprend alors la même session, sur le modèle de son lancement (gardé dans l'état du run).
4. Rebase sur la branche de départ, puis porte complète (`orchestrate.test` et `orchestrate.build` de `cadence.yaml`), jouée une seule fois. Si elle est rouge, la même session corrige une fois, puis la porte est rejouée. Un conflit au rebase est rendu à la même session (`--resume`), avec la liste des fichiers en conflit : elle le résout et finit le rebase. Si elle n'y arrive pas, le rebase est annulé et le run s'arrête en `conflit`, avec les fichiers nommés.
5. Intégration en avance rapide sur la branche de départ, puis le worktree est retiré. Rien n'est poussé. Le plan (`raf`) et `cadence deliver` restent ceux de la v1.

**La porte du run est celle de son commit, sur un environnement à jour (L764).** Les commandes de porte sont lues dans le `cadence.yaml` du worktree, après le rebase et de nouveau après une correction : un run qui corrige sa propre commande de porte est jugé par elle (le 17-11, un tel run restait rouge, la porte étant lue dans le dépôt principal). Quand elles diffèrent de celles de l'arbre principal, le journal le dit : « porte lue au commit du run (cadence.yaml changé par le run) : … — l'arbre principal (main) aurait joué : … » (une fois par changement, pas à chaque essai ni rebase), et, le run intégré, la même phrase est reprise dans le détail de l'état `integre` et sous sa ligne de fin, comme un conflit résolu (L723) : une porte affaiblie par le run (`--passWithNoTests`, `true`) se voit dans `cadence run --liste` et à la revue, pas au seul journal. Avant de jouer, la porte lit son environnement comme `cadence verify --gate` ([deliver](../deliver.md), « A stale environment ») : `node_modules` du worktree (liés depuis le dépôt) en retard sur le `package-lock.json` du run, Node du `PATH` (celui de la session du lead qui a lancé le run, figé à son ouverture) hors de `.nvmrc` ou `engines.node`. Périmé, rien n'est joué et aucune correction n'est demandée à la session : le run s'arrête en `environnement-perime`, avec chaque problème, sa remise à niveau (`cd <worktree> && npm ci`, `nvm install …` puis relancer la session) et la reprise : `cadence run --reponse <id> "environnement remis à niveau"`. `CADENCE_PORTE_ENV=jouer` joue la porte quand même.

**Le verdict de la porte du run vaut au push (L786).** Chaque porte complète jouée note son verdict (vert ou rouge) pour le commit qu'elle a jugé, dans `.git/cadence/gate-verdicts.json`, avec le même code que `cadence verify --gate` (`scripts/verdicts-porte.mjs`) : le hook pre-push accepte donc le sha intégré sans rejouer la porte (le 19-11, il le refusait « aucun verdict de la porte pour ce sha »). Sans commande de porte (`--sans-porte`), rien n'est noté. La porte du run joue les étapes de `verify --gate`, lues par le même code (`scripts/etapes-porte.mjs`) : `orchestrate.build`, puis `orchestrate.test`, en chaîne ou en parties, chaque partie dans son dossier (revue r1 : un test en parties était ignoré, et sur warhammer40k le run ne jouait que le build) ; un `test` que `verify --gate` refuserait n'est pas joué, le run s'arrête en `sans-porte` et le nomme. Le verdict n'est noté que pour un arbre égal à son commit : le sha est lu avant la porte, et rien n'est noté si `git status --porcelain --untracked-files=all` n'est pas vide avant ou après la porte, ou si `HEAD` a bougé ; le journal dit pourquoi (« porte du run : aucun verdict noté pour <sha> — … »), et le push demandera `verify --gate`. Voir [deliver](../deliver.md) pour les commits de plan seuls posés ensuite.

**Les commandes du projet qui appellent cadence sont jouées par le run (L781).** La session d'un run n'a pas le droit de lancer `cadence` ni `raf` : un projet dont `npm run news` appelle `cadence news build` (puis régénère son plan publié) voyait ses lots intégrés avec les données Nouveautés périmées (trois lots le 18-11, rejoués à la main par le lead). Le projet déclare ces commandes sous `run.regenerate` de `cadence.yaml` (liste de `{ command, dir }`, `dir` relatif au dépôt, la racine par défaut : [config](../config.md#generated-files-runregenerate)) ; le run les joue lui-même, dans le worktree, après le rebase et juste avant chaque porte. Rien n'est deviné d'un nom de script (revue r1 : la première version lisait `scripts.news` du `package.json` racine, et warhammer40k, qui le déclare dans `frontend/`, n'avait rien) : sans la clé, le run est celui d'avant. Ce qu'elles changent est commité en un commit du lot (`chore(<lot>): régénère les fichiers générés déclarés (cadence run <id>)`, hooks du dépôt compris, trailer `Cadence-Run-Regeneration: <id>`) ; rien à changer, aucun commit. La porte juge donc le commit intégré, fichiers générés compris. Une commande en échec, une clé mal formée, un commit refusé par un hook ou un fichier non commité que la régénération réécrit est rendu à la session comme une porte rouge, et ce qu'elle a écrit est remis comme avant ; cet échec a sa propre correction, il ne prend pas celle de la porte. Avant chaque rebase et chaque reprise de session (correction après porte rouge, `--reponse`, quota revenu), **tous** les commits de régénération du run sont retirés (revue r1 : une correction commitée par-dessus enterrait le premier, et le rebase suivant butait sur le fichier généré), puis rejoués sur l'arbre à jour : la session ne travaille jamais par-dessus, et deux runs qui ajoutent chacun une entrée ne se disputent pas le fichier généré. Le détail de l'état `integre` le nomme (« fichiers générés régénérés par le run avant la porte (run.regenerate, L781) : commit … »). Une sortie écrite dans un fichier ignoré par git est vue par la porte mais jamais commitée. Pourquoi pas autoriser `cadence news build` dans la session : un geste du programme ne s'oublie pas, et la session garde son interdiction de toucher au plan et aux vagues. Tests : `v2/test/run-regeneration-l781.test.ts` (dont un vrai `cadence news build` dans `frontend/`), `test/run-regenerate-config-l781.test.ts`.

**Le brief nomme les vérifications du projet quand le travail touche des fiches d'écran (L792, issue #68).** Le 19-11, une session chargée d'amener des fiches d'écran à « fiche valide » n'a jamais lancé `cadence spec check` : le brief n'en disait rien et interdisait `cadence`. Elle a reconstruit les règles depuis l'historique git et s'est crue à 0 écart ; 97 restaient. Quand le dossier des fiches (`orchestrate.spec.dir`, `docs/specs` par défaut) contient au moins une `<écran>/fiche.yaml`, ou quand la demande parle de fiches (d'écran, back, mixtes, `fiche.yaml`, `spec check`), ou quand le lot du plan a la spec (`spec: true`, ou `screen: page` qui l'implique ; sous-tâche comprise), le brief rendu reçoit, après la demande et le lot, un paragraphe « Vérifications du projet ». Il nomme `cadence spec check <fiche.yaml>` (une fiche par appel, et la boucle sur toutes), puis les commandes que `cadence.yaml` déclare : `orchestrate.build` et `orchestrate.test` (les étapes de la porte, parties comprises) et `orchestrate.accept` avec `CADENCE_ACCEPTATION`. La consigne : se fier à leur sortie, jamais à une relecture des règles. La ligne « N'utilise ni `raf` ni `cadence` » des deux briefs porte alors l'exception, et l'interdiction `Bash(cadence:*)` est remplacée par une interdiction par outil : tous ceux de `bin/cadence.js` sauf `spec`, plus `cadence spec green` et `cadence spec reseal` (gestes du lead). Les motifs de `--disallowedTools` ne savent pas dire « `cadence spec` sauf check|qa » (un refus `cadence spec:*` l'emporterait sur toute permission) : le reste de `cadence spec`, dont `cadence spec <lot> on|off` qui écrit le plan, est refusé par un hook PreToolUse, `v2/hooks/seul-spec-check.mjs` (devenu `cadence-permise.mjs` en L840), posé seulement dans ces sessions (revue r1). Il refuse tout segment de la commande qui lance `cadence` ou `raf` (avec chemin, `npx`, `npm|pnpm|yarn exec|dlx`, une version `cadence@latest` ou `@sylad/cadence@2.0.12`, `node …/cadence.js` ou `…/raf.js`, `node …/dist/cli.js` quand ce `dist` est celui du paquet cadence ou de son v2, `env` et `sudo` avec ou sans chemin et avec leurs options à valeur comme `sudo -u x`, affectations et `$(…)` compris) autrement que `cadence spec check|qa`. Le corps d'un heredoc (`<<'EOF'` … `EOF`, `<<-` compris) est du texte, pas une commande : un message de commit écrit par `git commit -F - <<'EOF'` peut avoir une ligne qui commence par `cadence …` ou `- raf …` (revue r2). Il lit le texte de la commande sans l'exécuter : une variable (`C=cadence; $C spec L1 on`, `"$(which cadence)"`), `eval`, `xargs`, `sh -c '…'` ou `bash -c '…'` et les mots coupés par un échappement (`c\adence`) ne sont pas lus. C'est un garde contre l'accident, pas une frontière : la session peut aussi écrire `.cadence/raf.yaml` avec l'outil Edit. `cadence spec check` et `spec qa` ne font que lire une fiche : la session ne touche toujours ni au plan, ni aux vagues, ni aux livraisons. Le choix est gardé dans l'état (`spec_check`), et une reprise (`--reponse`, porte rouge, quota) garde les mêmes interdits. Sans fiche ni demande qui en parle, le brief et les interdits ne changent pas. Code : `scripts/commandes-du-brief.mjs`, hors de `v2/src` comme `scripts/etapes-porte.mjs` : les règles anti-rechute de v2 (C1) y bannissent le vocabulaire des fiches, et le run ne juge d'ailleurs rien contre une fiche, il nomme la commande qui le fait. Tests : `v2/test/run-verifications-l792.test.ts`, sur le texte du brief rendu et les arguments passés à claude (un outil ajouté à `bin/cadence.js` sans être interdit fait échouer le test).

**`cadence analyse` est permise dans toute session de run (L840).** Le 25-11, 5 runs d'adoption de l'analyse sur 6 (jobmail L23 et L24, evatosorus L54, discotheque L25, ol L270) se sont arrêtés sur une question : la session voyait `cadence analyse --init`, et même `--help`, refusées par l'interdiction `Bash(cadence:*)` posée sur toute session de run (et, quand des fiches étaient nommées, par l'interdiction par outil et le hook de L792, qui ne laissaient que `spec check|qa`). L'interdiction `Bash(cadence:*)` est désormais remplacée dans toute session par une interdiction par outil (`interditsDuRun`) : tous ceux de `bin/cadence.js` sauf `analyse`, plus `cadence spec` entière sans fiche nommée, ou seulement `spec green` et `spec reseal` avec. Le hook de L792, renommé `v2/hooks/cadence-permise.mjs`, est posé dans toute session (`--spec` quand le brief nomme `cadence spec check`) : il laisse passer `cadence analyse` sans option, avec `--init`, `--contre <ref>`, `--outil <nom>` ou `--help` (chacune une fois ; une redirection, `2>&1`, `>&2`, `&>/dev/null`, `2>&-` comprises, est retirée avant l'examen des options et son `&` ne coupe pas la commande : revue r1, M1), et refuse `--ecrire` et `--migrer` (ils réécrivent une ligne de base), toute autre option, et tout autre cadence ou raf, avec la même lecture de la commande qu'en L792. Quand la demande ou le lot du plan (titre, notes) cite `cadence analyse`, la clé `analyse:`, ou « analyse statique » (un simple « analyse du besoin » ne suffit pas, ni un identifiant de demande `D-<n>`, propre au registre de chaque dépôt : revue r1, M2), `docs/analyse.md` du paquet est jointe comme pièce (mode complet, à lire avant d'écrire) et nommée dans le brief ; un dépôt qui déclare `analyse:` voit la commande nommée sans la pièce. La ligne « N'utilise ni `raf` ni `cadence` » porte alors l'exception (`leverPourCadence`). Tests : `v2/test/run-analyse-permise-l840.test.ts`, qui joue dans une session de run factice les deux gardes de Claude Code (motifs de `--disallowedTools`, puis hooks PreToolUse des réglages) : `cadence analyse --init` permise, `cadence deliver` refusée.

**L'entrée Nouveautés d'un lot visible est demandée, et son absence se voit (L794).** Le 20-11, deux lots visibles (finance L182, warhammer L67) ont été rendus par `cadence run` sans entrée Nouveautés, deuxième occurrence : le brief disait d'ignorer les « Nouveautés imposées par l'outil », lu par certaines sessions comme « pas d'entrée ». Quand le lot du run est visible dans le plan (`visible: true`, ou un `screen:` ; sous-tâche comprise, plan au format mappé lu avec ses clés `plan.lots` et `plan.fields`), le brief rendu reçoit après la demande un paragraphe « Entrée Nouveautés (obligatoire) » : l'entrée s'écrit à la main dans `docs/nouveautes/`, au format des entrées voisines (`title` côté utilisateur, `date`, `created` avec fuseau, `lots: [<lot>]`, `captures`), avec une capture rangée comme les autres (seule capture qui va dans le dépôt) ou `nocapture: <raison>`, commitée avec le lot, sans commande `cadence` ; quand le projet déclare `run.regenerate`, il dit aussi que le run reconstruit les fichiers générés. La ligne « N'utilise ni `raf` ni `cadence` » du brief léger dit désormais qu'une entrée demandée s'écrit quand même. À la fin du run, intégré ou non, les entrées du commit du run (lues dans git : un fichier non commité ne compte pas) qui citent le lot sont relevées : sans aucune, une ligne « Nouveautés manquante : le lot <lot> est visible et aucune entrée de docs/nouveautes/ ne le cite au commit du run — à écrire avant la livraison », sinon « Nouveautés : <entrées> ». L'état garde `lot_visible` et `nouveautes: { entrees, manquante }`, et `--liste` ajoute « Nouveautés manquante (lot visible <lot>) ». L'intégration n'est jamais bloquée : le lead écrit ou fait écrire l'entrée avant la livraison. Code : `scripts/nouveautes-du-run.mjs` (la lecture du plan y est partagée avec `lotAFiches`, L792). Tests : `v2/test/run-nouveautes-l794.test.ts`, sur le texte du brief rendu, l'état, le journal et `--liste`.

**La branche de départ avance pendant la porte (L723).** C'est le cas quand un autre run s'y intègre pendant la porte, ce qui est arrivé deux fois le 13-11 : chaque fois, un run de 15 à 35 min s'est arrêté en `refus-integration` et a été repris à la main. Désormais, le run recommence l'étape 4 sur la nouvelle tête de la branche (rebase, conflit rendu à la session, porte), puis retente l'avance rapide. Le journal le dit : « main a avancé pendant la porte : rebase et porte rejouée (2/3) ». Au bout de trois rebases, si la branche avance encore, le run s'arrête en `refus-integration`, avec la raison. Si l'arbre principal a des modifications non commitées (ou des fichiers non suivis) sur des fichiers que le run modifie aussi, git refuserait l'avance rapide avec « Your local changes would be overwritten ». Le run s'arrête alors en `refus-integration`, avec un message qui nomme ces fichiers et donne la commande de reprise (`cadence run --reponse <id> "intègre"`, une fois ces fichiers commités ou mis de côté). Une modification sur un autre fichier n'empêche rien.

**Le run ne tient que ses fichiers (L796, issue #70 du compte pro).** Jusqu'ici, un run tenait toute la branche de départ : le pre-commit refusait tout commit du lead pendant 30 à 60 min, même une doc ou le plan d'un autre lot. Le fichier qui tient la branche (`<git-common-dir>/cadence/tenu/run-<pid>.json`) porte désormais le `worktree` du run. Au commit du lead, le pre-commit lit les fichiers du run à cet instant : ce que son worktree change depuis l'ancêtre commun avec la branche, commité ou non, plus ses fichiers non suivis. Il compare cette liste aux fichiers du commit (l'index du hook, `commit -a` compris). Un commit disjoint passe. Un commit qui touche un fichier du run est refusé, et le refus nomme les fichiers communs. Une porte jouée dans l'arbre principal, ou un fichier tenu sans `worktree`, tient encore toute la branche. Les écritures de `raf` (L695, L722, L779) restent mises en attente : L779 n'est pas défait.

**La branche a avancé sur des fichiers disjoints : rebase, porte rejouée sauf plan seul (L796).** Si la branche a avancé pendant la porte, le run compare les fichiers des commits arrivés à ceux de son propre diff. Disjoints, il se rebase (sans conflit possible). « Disjoint » ne compare que des chemins : un test, un module importé par le code du run, `package.json`, `package-lock.json`, `tsconfig.json` ou `v2/budget.json` arrivés changent ce que la porte juge (revue r1). La porte est donc rejouée sur le sha rebasé avant l'avance rapide ; ce rejeu ne compte pas parmi les trois rebases de L723 : un commit disjoint ne rend plus le lot, il coûte une porte (10 avances disjointes de suite au plus, puis le chemin de L723). Le journal et le détail de l'état `integre` le disent : « main a avancé pendant la porte sur des fichiers que le run ne touche pas (1 commit : …) : rebasé, porte rejouée sur le sha rebasé (L796) ». Seule exception : si tous les commits arrivés ne touchent que le plan (`.cadence/raf.yaml`, `docs/plan/`) ou le registre (`.cadence/demandes/`), que la porte ne lit jamais, le run intègre sans rejouer la porte et le dit (« … rebasé, intégré sans rejouer la porte, qui a jugé <sha> : ils ne touchent que le plan ou le registre des demandes, que la porte ne lit pas (L796) »). Le sha intégré n'a alors pas de verdict noté (L786) : là où le hook pre-push de la porte est installé, il demandera `cadence verify --gate` à ce sha ; maritime-atlas n'a pas ce hook. Ce n'est pas disjoint si un commit arrivé change `cadence.yaml` (la porte), ou si le run a un commit de régénération (L781). Le chemin de L723 s'applique alors : rebase, porte rejouée, conflit rendu à la session, `conflit` s'il n'est pas résolu, `refus-integration` après trois rebases. Tests : `v2/test/run-disjoint-l796.test.ts`, `test/run-verrou-fichiers-l796.test.ts`.

**Le `raf start` du lot laissé non commité est commité par le run (L796).** `raf start <lot> && cadence run --lot <lot>` laissait le plan modifié dans l'arbre principal. Un run qui touchait aussi le plan finissait en `refus-integration` à cause de son propre start, et environ 50 min ont été perdues avant que le lead le voie. Au lancement, avant d'ouvrir le worktree, le run compare le plan non commité à celui de HEAD. S'il n'en diffère que par le statut du lot (et sa date `started`), le run le commite lui-même (`plan: <lot> démarré`, ou le gabarit `plan.commit` du projet), hooks compris, et le dit : « raf start L1 laissé non commité : commité par le run (…) ». Le worktree part de ce commit. Si le plan porte d'autres changements, rien n'est commité et l'avertissement des fichiers non commités reste celui d'avant.

**Un conflit résolu reste visible (L723, revue).** La session qui résout un conflit de rebase répond « fini » ; ce mot ne remplace plus le rapport du travail (`rapport` de l'état). Chaque conflit est ajouté à l'état (`conflits` : branche, sha de la cible, fichiers, `resolu`, dernier message de la session), qu'il soit résolu ou non. `resolu` est absent tant que la session y travaille, faux si elle ne l'a pas résolu. Une reprise de la session pendant une résolution (quota revenu, `--reponse`) la continue : le rapport du travail reste, et le dernier mot de la reprise va au conflit ; le rebase coupé est annulé puis rejoué. Ses messages vont à `messages` avec `sujet: "résolution du conflit au rebase"`, et le journal les écrit sous ce nom (`session, résolution du conflit au rebase, fin (ne remplace pas le rapport du travail) : …`). Un run intégré après un conflit résolu le dit dans son détail et dans sa ligne de fin (« conflit au rebase sur main (<sha>) résolu par la session, fichiers : … ; la session : … ») : la fusion a été écrite par la session, elle est à relire. Tests : `v2/test/run-rebase-l723.test.ts`.

**Une correction après porte rouge reste visible (L724).** Même modèle que le conflit résolu (L723). Quand la porte complète est rouge, la session est reprise pour corriger ; son « fini » ne remplace plus le rapport du travail (`rapport` de l'état). Chaque correction est ajoutée à l'état (`corrections` : `rouge`, la sortie de la porte ; `message`, le dernier mot de la session ; `verte`, vrai si la porte rejouée ensuite passe, faux si elle reste rouge). Ses messages vont à `messages` avec `sujet: "correction après porte rouge"`. Le journal donne la sortie rouge (« porte rouge : reprise de la session pour corriger : … »), puis la fin de la correction (`session, correction après porte rouge, fin (ne remplace pas le rapport du travail) : …`), puis la porte verte (« porte rouge (<commande> … <dernière ligne>) corrigée par la session, porte verte ensuite ; la session : … »). Un run intégré redit cette ligne dans son détail et dans sa ligne de fin. La réponse du lead à un run en `porte-rouge` (`cadence run --reponse`) est aussi une correction, comme la reprise après un quota pendant une correction. Tests : `v2/test/run-porte-rouge-l724.test.ts`.

**Aucun processus ne survit au run (L837).** Vécu le 24-11 : `astro preview --port 4391`, lancé en arrière-plan par la session d'un run, vivait encore 26 min après sa fin. Pendant qu'il joue, le run pose `CADENCE_RUN_PROCESSUS=<id du run>` dans son environnement : la session, la porte et tout ce qu'elles lancent en héritent, y compris un serveur détaché par `setsid`, `nohup` ou l'outil Bash d'arrière-plan, qui sort de tout groupe de processus (pgid) et que l'enveloppe de la session (`setsid`, groupe tué au retour) ne voyait donc pas. Ces processus marqués forment le groupe du run. À chaque fin (intégré, rendu, échec, attente d'une réponse, quota), le run envoie SIGTERM à chacun, leur laisse 3 s, puis SIGKILL à ceux qui restent, et recommence tant qu'il en trouve (trois passes au plus). La fin le dit : `processus du run <id> arrêtés (N) : <pid> (<commande>), …`, et `processus du run <id> ENCORE VIVANTS après SIGKILL (N) : … — kill -9 …` s'il en reste ; l'état garde les pids (`processus`). Un run qui ne laisse rien n'écrit rien. Le run lui-même et ses ancêtres ne sont jamais visés, ni un processus d'un autre run (une autre marque) ou sans marque. Un run tué par un signal ne joue pas sa fin : pour un run `--fond`, le veilleur arrête son groupe dès que le run meurt, avant d'écrire la cause d'arrêt (la dernière cause du journal reste celle du run) ; sinon `--reponse` sur un run interrompu et `--clore` l'arrêtent avant tout. Le contrôle lit `/proc` ; sans `/proc`, la fin dit que rien n'a été contrôlé. Code : `v2/src/processus.ts` ; tests : `v2/test/run-processus-l837.test.ts` (serveurs `setsid` et `nohup` de la session, serveur de la porte, processus qui ignore SIGTERM, run `--fond` tué par SIGKILL, `--clore`, et un autre run qui survit).

**Quota (L700, D-15).** En `claude -p`, la fin de quota ne se reconnaît qu'au texte du résultat (doc officielle lue le 11-11). **Run intégré à la main, `--clore` et `--archives` (L745, issue #62 du compte pro).** Un run fini sans intégration (`conflit`, `refus-integration`, `porte-rouge`…) garde son worktree et sa branche. Quand le lead intègre ensuite ses commits à la main sur la cible, `--liste` disait encore `conflit` trois jours plus tard, et retirer le worktree et la branche à la main n'y changeait rien (la liste lit l'état du run).

Quatre passes ont cherché à **prouver** qu'un run était intégré avant de le supprimer (commits ancêtres de la cible, contenu des fichiers, patch-id, tableau de dix cas), et quatre revues ont trouvé chaque fois un cas où la preuve était fausse et où `--clore` supprimait la seule copie d'un travail. La cinquième passe change la conception : **`--liste` ne fait qu'afficher, et `--clore` ne retire rien qu'il n'ait d'abord archivé**. Il n'y a plus de preuve à établir, donc plus de patch-id, plus de reconnaissance par le contenu, plus de tableau, et `--force` n'existe plus : il servait à passer un refus, et `--clore` ne refuse plus un run parce qu'il n'est pas intégré. Code : `v2/src/run/clore.ts` ; tests : `v2/test/run-clore-l745.test.ts` (chaque cas des quatre revues y finit avec le travail encore atteignable par une référence).

### `--liste` : affichage seul

- `integre a la main (était conflit ; worktree et branche : cadence run --clore <id>)` seulement quand la tête de la branche du run est un **ancêtre** de la cible (`git merge-base --is-ancestor`) et que le run a au moins un commit. Branche retirée à la main : la tête notée dans l'état à la fin du run (`tete`) en tient lieu.
- Tout autre cas garde l'état du run (`conflit`, `porte-rouge`…), suivi d'une ligne `commits absents de la cible : N` (`git rev-list --count <tête> --not <cible>`) et de la commande `--clore`. Un cherry-pick, un rebase, un squash ou un conflit résolu à la main sur la cible ne sont donc jamais reconnus : le run reste `conflit`, et c'est sans conséquence puisque `--clore` le clôt quand même sans rien perdre. `N` vaut `inconnu (raison)` quand git échoue ou que la tête ou la cible manque, et `0 (le run n'a aucun commit)` pour un run sans commit.
- Un run clos s'affiche `integre a la main (main = <sha>), clos le <date> (était conflit)` s'il était intégré au moment de la clôture, sinon `clos le <date> sans intégration, travail archivé : cadence run --archives (était conflit)` ; ce qui est resté sur place (worktree gardé, branche gardée) suit dans la parenthèse.

### `--clore <id>` : archiver, vérifier, puis retirer

`--clore` clôt un run fini, intégré ou non. Il refuse seulement un run qui se reprend encore (`en-cours`, `interrompu`, `attente`, `quota`, ou dont un processus tient le verrou) et un run déjà intégré par `cadence run`. Dans l'ordre :

1. **Les têtes connues du run**, chacune avec sa référence d'archive : la tête de sa branche (`refs/cadence/archive/<id>`), le HEAD de son worktree tel que `git worktree list --porcelain` le donne, détaché compris et dossier supprimé à la main compris (`refs/cadence/archive/<id>-worktree`), et la tête notée à la fin du run tant que git a l'objet (`refs/cadence/archive/<id>-fin`). Une même tête n'a qu'une archive.
2. **Les archives sont posées puis relues** (`git update-ref`, puis `git rev-parse --verify`). Une archive du même nom déjà posée sur un autre commit n'est jamais écrasée. Si une commande git échoue ou si une archive ne se relit pas, `--clore` refuse (code 1, « rien n'a été retiré ») et ne touche à rien. Une absence (branche retirée) se lit par le code 1 de `git rev-parse --verify -q` ; tout autre code est un échec, jamais une absence.
3. **Le dossier du worktree n'est retiré que s'il est propre**, par `git worktree remove` **sans** `--force`. Il reste, et la commande dit pourquoi, quand : `git status --porcelain --untracked-files=all --ignore-submodules=none` y liste un fichier modifié ou non suivi (le réglage `status.showUntrackedFiles=no` ne cache rien) ou échoue ; git refuse de le retirer (un sous-module initialisé : ses commits non poussés ne vivent que dans `.git/worktrees/<id>/modules` ; un dossier qui n'est plus un worktree) ; le dossier existe mais git ne le connaît pas comme worktree du dépôt ; le dossier a été supprimé à la main (son entrée reste à `git worktree prune`). Un worktree gardé qui était sur la branche du run passe en HEAD détaché sur le même commit (`git checkout --detach`, aucun fichier ni l'index ne changent), pour que la branche puisse être retirée.
4. **La branche est retirée** (`git branch -D`), seulement si sa tête vient d'être archivée. Si git refuse, elle reste et la commande le dit.
5. **L'état note `clos`** : date, cible, tête, `integre`, `archives`, et `restes` (ce qui est resté sur place). La sortie donne les archives avec leur sha court et ce qui reste. `cadence run --reponse` refuse un run clos.

Hypothèse retenue : un worktree qui contient un sous-module initialisé n'est jamais retiré, même si tous ses commits sont poussés. C'est plus strict que « aucun commit de sous-module non poussé », et c'est le refus de git lui-même.

Limites, écrites pour qu'on ne les découvre pas : les fichiers ignorés par `.gitignore` du worktree (un `.env` local, `node_modules`) ne comptent pas comme des modifications et partent avec un worktree propre, comme après une intégration par `cadence run` ; un commit qui n'est atteignable que par le reflog du worktree ou de la branche (défait par `git reset`, remplacé par `--amend` après la fin du run) ou par une référence propre au worktree (`refs/bisect/*`, `refs/worktree/*`) n'a pas d'archive, seules les têtes en ont une. L'intégration normale par `cadence run` retire toujours son worktree avec `--force` : tout son travail vient d'être avancé sur la cible, mais un commit fait dans un sous-module du worktree et jamais poussé y est encore perdu (cas B2 de la quatrième revue, hors de `--clore`).

### `--archives` : retrouver un travail archivé

`cadence run --archives` liste chaque archive (`git for-each-ref refs/cadence/archive/`) avec son sha court, la date et le sujet du commit, et sous chacune la commande qui en refait une branche : `git branch archive-<id> refs/cadence/archive/<id>`. Les archives sont des références locales : git ne les ramasse jamais (`git gc`), ne les pousse pas, et elles ne paraissent pas dans `git branch`. Pour en retirer une, quand on est sûr de ne plus en vouloir : `git update-ref -d refs/cadence/archive/<id>`.

### Run qui se reprend, déjà intégré à la main (L767)

Le 17-11, deux runs intégrés à la main n'étaient pas clos, worktree gardé. Pour un run qui se reprend, `--liste` ne regardait pas la cible (il montrait son état et la commande de reprise) et `--clore` le refusait (« il se reprend »). Un run `interrompu`, `attente` ou `quota` **dont aucun processus vivant ne tient le verrou** et dont la tête est un ancêtre de la cible (même règle que ci-dessus, au moins un commit) s'affiche donc `interrompu, sa tête est sur main (<sha>) : intégré à la main ? worktree et branche : cadence run --clore <id>`, et `--clore` le clôt comme un run fini (archives d'abord, worktree retiré seulement s'il est propre). Un run en cours, ou en quota avec son processus qui attend, n'est jamais lu ni clos ; un run qui se reprend et n'est pas sur la cible reste refusé.

### `--purger` : vider le dossier des runs (L767)

Le dossier `../.cadence-run/` gardait tout : 51 dossiers de captures et 174 fichiers d'état le 17-11. `cadence run --purger` retire, pour chaque run **du dépôt courant** fini depuis plus de N jours, ses fichiers à côté de l'état et du worktree : l'état (`<projet>-<id>.json`), le verrou, `<worktree>.captures/`, `<worktree>.question.md`, `<worktree>.reglages/`, et son journal `fond-<id>.log` quand plus aucun run gardé ne le cite. `--dry-run` liste les mêmes lignes (`à purger <id> (intégré le <date>) : <fichiers>`) sans rien retirer. Les archives git (`refs/cadence/archive/`) restent.

- **Candidats** : un run `integre` (fini à la dernière écriture de son état) ou clos par `--clore` (fini à sa date de clôture), dont le dossier du worktree n'existe plus et dont aucun processus ne tient le verrou. Tout autre run n'est jamais touché : en cours, interrompu, en attente d'une réponse, en quota, rendu au lead (`conflit`, `porte-rouge`…), même worktree disparu. Un run fini et ancien dont le worktree est gardé est nommé (`gardé <id> : worktree gardé : <chemin>`) ; le retirer, puis relancer la purge. L'état est retiré en dernier : un échec au milieu laisse le run listé, et la purge suivante reprend.
- **Délai** : `run.purgeAfterDays` du `cadence.yaml` du dépôt, 14 par défaut ; `0` prend tout run fini. Une autre valeur qu'un entier positif ou nul est refusée (code 1) avant toute suppression.

```yaml
run:
  purgeAfterDays: 14
```

Code : `v2/src/run/purger.ts` ; tests : `v2/test/run-purger-l767.test.ts`.

Le lanceur choisit désormais l'id du run (heure à la seconde et son pid, que deux processus vivants ne partagent pas), nomme le journal `../.cadence-run/fond-<id>.log`, le crée en exclusif (un journal déjà là n'est jamais repris) et passe l'id au run par `CADENCE_RUN_ID`, que le run ne transmet pas à ses sessions `claude`. La ligne du lancement le dit (`cadence run <id> lancé en arrière-plan ; journal : …`) ; l'état du run cite son journal (`journal`), par où `--liste` (cause d'arrêt d'un run interrompu) et `--purger` le retrouvent. Test : `v2/test/run-fond-journal-l773.test.ts` lance deux vrais runs `--fond` dans la même seconde et vérifie deux journaux distincts, chacun nommé d'après son run, cité par son état, sans une ligne de l'autre, puis `--liste` et `--purger --dry-run`.

**Un run arrêté sans raison : ce que joindre à une issue (L711, issue #55 du compte pro).** Le 12-11, un run `--fond` est mort à la fin de la session Claude Code qui l'avait lancé, sans rien laisser dans son journal ; la cause n'a pas été reproduite sur Big-Blue. Le journal d'un run `--fond` (`../.cadence-run/fond-<id>.log`, chemin donné au lancement) garde désormais de quoi l'établir au prochain cas. **Joins ce fichier entier à l'issue**, avec la ligne de `cadence run --liste` du run. On y lit :

- au lancement, l'identité du processus du run : `processus du run (2026-11-12 18:28:03) : pid 1544714, pgid 1544703, sid 1544703, ppid 1544703, cgroup 0::/init.scope`. Le cgroup ne s'écrit que si `/proc/self/cgroup` existe ; sans `/proc`, pgid et sid viennent de `ps`, ou valent `?` ;
- chaque signal reçu, avec l'heure, sur une ligne qui commence par `cause d'arrêt` : celui reçu par le groupe du run (SIGHUP, SIGTERM, SIGINT), celui reçu par l'enveloppe de la session `claude`, celui qui a arrêté le processus du run, avec son code (`a reçu SIGHUP et s'est arrêté (code 129)`), et celui sur lequel `claude` lui-même est mort (`la session claude s'est arrêtée sur SIGKILL (code 137)`) ; une session arrêtée par son délai de 4 h l'écrit ainsi (`délai de 4 h dépassé`), pas comme un SIGTERM venu d'ailleurs, et un SIGINT à l'enveloppe reste SIGINT (code 130).

`--liste` ajoute à un run `interrompu` la dernière ligne `cause d'arrêt` de son journal. L'arrêt lui-même ne change pas : le run est synchrone (il attend `claude` pendant toute la session), donc un gestionnaire de signal dans son processus ne s'exécuterait qu'à la fin de la session, et le run ne s'arrêterait plus au signal. `--fond` détache donc un veilleur (`cadence run --veilleur`, usage interne), qui lance le run, ne transmet ni n'arrête rien, et écrit ce que le run ne peut pas écrire lui-même (`v2/src/trace.ts`) ; un signal qu'il reçoit l'arrête après l'avoir écrit, comme un processus sans gestionnaire (le run continue, sauf s'il a reçu le même signal) ; le run apprend le chemin de son journal par la variable `CADENCE_RUN_JOURNAL`, qu'il ne transmet pas à ses sessions `claude`. Un signal envoyé à `claude` seul, qui est dans sa propre session, ne se voit qu'à sa mort. Tests : `v2/test/run-signal-l711.test.ts` (un run factice reçoit SIGTERM, le journal le dit avec l'heure, `--liste` l'affiche ; SIGTERM au groupe, l'enveloppe et le veilleur l'écrivent ; `claude` mort sur un signal).

**Le rapport de la session reste celui de la fin du travail (issue #57 du compte pro).** Le 13-11, un run `--fond` fini `integre` n'avait gardé, dans son journal et son état, que le dernier message de sa session : la réponse à une notification de tâche (un agent de fond qui finissait en retard). Le rapport donné en finissant le travail (commits, tests scellés à resceller, vérifié / non vérifié, hypothèses) n'était plus que dans le transcript. Cause : en `--output-format json`, `claude -p` ne rend que le message final du dernier tour, et une notification arrivée après le rapport ouvre un tour de plus. Les sessions du run (et des bras du banc, même `argsClaude`) parlent donc en `--output-format stream-json --verbose`, où chaque tour finit par un événement `result`. `v2/src/rapport.ts` compte les tours sur ces `result` : le tour 1 est celui du prompt, qui fait le travail ; tout tour suivant a été ouvert après lui. Dans un vrai flux (claude 2.1.293, capturé le 13-11), la notification est un événement `system/task_notification`, pas un message `user`, et la réponse tardive cite volontiers le rapport (« Fini : la commande en arrière-plan a bien terminé ») : ni le format de la notification ni le mot « fini » ne servent donc à choisir. Le rapport (`rapport` de l'état) était le dernier message sans appel d'outil du tour 1 (depuis L728 : le dernier message marqué `=== FINI ===`, voir ci-dessous) ; une notification absorbée pendant ce tour ne change rien. Rien n'est remplacé : l'état ajoute chaque message avec son tour (`messages`, `{ texte, tour }`), et le journal les écrit tous dans l'ordre (`session, pendant le travail : …`, `session, rapport : …`, `session, tour 2, après le rapport (ne change ni le rapport ni l'état du run) : …`). Un tour tardif ne décide plus de l'état du run : l'échec, l'id de session et le texte où l'on reconnaît un quota viennent du `result` du tour du rapport (depuis L728, le tour du message marqué, voir ci-dessous), et le code de sortie n'est compté que si aucun tour n'a commencé après lui ; seuls le coût et les jetons viennent du dernier `result`, qui les cumule. Les messages sont gardés quelle que soit la fin de la session : travail fini, mais aussi échec (`error_max_turns`, erreur d'API), délai de 4 h dépassé, signal reçu ou quota atteint ; c'est là que le lead lit ce qui a été fait et ce qui reste. Dans ces fins-là, l'état ne reçoit pas de `rapport` (le travail n'a pas fini) et le journal nomme le dernier message pour ce qu'il est (`session, dernier message avant l'arrêt (travail non fini) : …`) ; le détail d'un échec nomme l'erreur et la cite (`session <id> : error_max_turns, code 1`, `session <id> : erreur (« API Error: 500 … »)`, `session arrêtée avant son result (SIGTERM) ; dernier message : …`), jamais « success ». Tests : `v2/test/run-rapport-57.test.ts`, sur deux flux réels (`v2/test/fixtures/flux-notification-tardive-2.1.293.jsonl`, `…-pendant-le-travail-2.1.293.jsonl`) et des flux construits (erreur, code ou quota d'un tour tardif ; flux coupé ; ancienne sortie json ; un run complet par fin de session : échec, délai, signal, quota, bascule Opus → fable).

**Le rapport d'une session est le message qu'elle marque (L728, issue #58 du compte pro).** L'inverse de #57 : une session `--fond` a fini le tour du prompt sur une ligne d'attente (« La recette navigateur complète tourne ; je surveille les échecs et sa fin. ») ; sept tours ont suivi, chacun ouvert par une notification de tâche, et le dernier tenait le vrai rapport. L'état gardait la ligne d'attente. Deviner le rapport à la forme du flux (tour du prompt, outils appelés, tâches de fond actives, `system/task_started` et `task_notification`) a cédé cinq fois dans la journée : la revue de L728 a montré qu'un Read tardif de la sortie d'une tâche, après un rapport donné pendant qu'elle tournait, remplaçait encore le rapport (#57 revenait), et qu'un rapport tardif donné sans outil passait pour un run normal. Le lecteur ne devine donc plus : la session le dit. Les briefs de `cadence run` (`v2/briefs/bras-A.md`, `bras-sequence-v2d.md`) demandent que le rapport final soit un seul message qui commence par la ligne `=== FINI ===`, seule sur sa ligne, et que cette ligne n'apparaisse nulle part ailleurs (ni ligne d'attente, ni réponse à une notification de tâche, ni message de commit) ; les consignes de reprise (quota revenu, bascule Opus → Fable, conflit de rebase, porte rouge) demandent la même chose (`CONSIGNE_FINI`, `v2/src/rapport.ts`, où `MARQUEUR` est défini une fois). Le rapport retenu est le **dernier** message qui commence par cette ligne (`rapport` et `rapport_tour` de l'état, le message marqué `marque: true` dans `messages`) ; le `result` de son tour décide de l'état (échec, quota, session), et tout ce qui vient après lui (dans son tour ou un tour suivant) est marqué `apres` : au journal (`session, tour N, après le rapport (ne change ni le rapport ni l'état du run) : …`), jamais à la place du rapport. Le journal écrit `session, rapport : …` (tour 1) ou `session, rapport (marqué, tour N) : …` ; la ligne de fin et `cadence run --liste` ajoutent `rapport marqué, tour N`. Sans aucun marqueur, le lecteur ne choisit pas : le rapport est le dernier message de la session, le dernier tour décide (une session coupée pendant un tour qui suit l'attente reste un échec, un quota au dernier tour compte), l'état porte `rapport_sans_marqueur: true`, le journal écrit `session, rapport (sans marqueur : le dernier message de la session, à vérifier) : …`, et la ligne de fin comme `--liste` disent `rapport sans marqueur : à vérifier dans le journal`. Tests : `v2/test/run-rapport-58.test.ts`, sur les deux flux réels capturés le 13-11 (`v2/test/fixtures/flux-attente-tache-de-fond-2.1.293.jsonl`, `flux-notification-tardive-2.1.293.jsonl`), bruts (sans marqueur : à vérifier) et avec le marqueur mis dans le message qu'une session qui suit le brief aurait marqué (rapport au tour 2 pour #58, au tour 1 pour #57), sur les deux cas de la revue (Read tardif après un rapport marqué ; rapport marqué dans un tour tardif sans outil), plusieurs marqueurs, session coupée, et sur les briefs et consignes eux-mêmes ; `run-rapport-57.test.ts` rejoue #57 avec le marqueur.

**Une session qui attend une commande en arrière-plan (L763, issue #63 du compte pro).** Le 17-11, deux runs sont restés bloqués 21 et 55 min : leur session avait lancé une commande avec `run_in_background`, et une session `claude -p`, sans interface, n'est jamais réveillée par la fin d'une telle commande. Elle attend sans fin, sans rien écrire. Deux gardes :

- **Le refus.** Les réglages de chaque session du run (`--settings`, `reglagesRun` de `v2/src/socle.ts`) portent un hook `PreToolUse` sur `Bash` (`v2/hooks/premier-plan.mjs`) : un appel avec `run_in_background: true` est refusé (code 2), avec un message qui dit de relancer la même commande au premier plan, avec un timeout à la hauteur de sa durée, porte du dépôt comprise. Les mêmes réglages posent `BASH_MAX_TIMEOUT_MS` (variable de Claude Code, clé `env`) à 30 min, la durée permise à une commande de la porte (`PORTE_MS`) : la porte entière tient dans un appel au premier plan. Le hook de lecture du mode complet reste, le refus s'y ajoute. Le banc ne prend pas ce hook.
- **Le signalement.** `cadence run --liste` ajoute à un run `en-cours` dont la session est vivante la note `session bloquée ? aucune commande en cours et rien d'écrit depuis N min (seuil S min) ; reprendre : kill <pid> (la session claude), puis cadence run --reponse <id> "reprends"` quand trois conditions tiennent : le processus `claude` du run tourne (un descendant du porteur du verrou dont la ligne de commande porte l'id de session) ; aucun shell n'est son enfant direct (l'outil Bash de Claude Code joue chaque commande dans un shell enfant ; un serveur MCP n'en est pas un) ; son transcript (`~/.claude/projects/<worktree>/<session>.jsonl`, ou `$CLAUDE_CONFIG_DIR`, sous-agents compris) n'a pas été écrit depuis le seuil (sans transcript : l'heure de l'état, écrit au départ de chaque session). Seuil : 15 min par défaut, `--inactif <minutes>` le change. Pendant la porte et l'intégration, `claude` ne tourne pas : rien n'est signalé. Arrêter `claude` termine la session en échec et rend le verrou ; `--reponse` reprend alors la même session, dans le même worktree. Code : `v2/src/inactif.ts` ; tests : `v2/test/run-inactif-l763.test.ts` (refus et passage du hook, réglages en mode léger et complet, signalement sur un arbre de processus simulé et sur de vrais processus par `--liste`, seuil, usage).

**Le run prend un créneau (L710, issue #55 du compte pro).** Le 12-11, `cadence lead tour` affichait « créneaux libres : 3 sur 3 » pendant que deux runs tournaient : le registre des créneaux ne voyait que les vagues et les sessions du lead. Pendant sa session, sa porte et son intégration, le run s'inscrit dans le registre commun (`$CADENCE_HOME/runs/<id>.json`, `CADENCE_HOME` valant `~/.cadence/orchestrate` par défaut, comme pour `orchestrate`), puis s'en retire à la fin (`inscrireCreneau`, `v2/src/verrou.ts`). Il compte tant que son état est `en-cours` et qu'un processus vivant tient son verrou : c'est le contrôle de `interrompu` dans `--liste`. Un run mort, fini, en attente ou en quota ne compte pas. `cadence lead tour`, `cadence orchestrate --status` et la bande `cadence-hud` l'ajoutent aux sessions en cours ; les deux premiers le nomment (`runs cadence run : 1 (projet <id>)`), la bande lui donne sa propre ligne avec son état (L687, [cadence-hud](../cadence-hud.md)), selon la formule de [concepts.md](../concepts.md#slots-and-holds). Les vagues l'attendent comme une session du lead, et leur journal le cite (`… en cours : w1, cadence run <id>`). Tests : `test/creneaux-runs-l710.test.ts` (registre et bande sur le même registre : un run vivant compte, un pid mort ne compte pas, une vague attend) et `v2/test/run-creneau-l710.test.ts` (l'inscription pendant la session, puis son retrait).

**Socle de la session (L705, D-7).** Chaque session du run reçoit, par son `--settings`, trois coupes mesurées sur de vraies sessions le 12-11 ([mesure](../mesures/socle-session-2026-11-11.md#coupes-appliquées-l705-2026-11-12)) : les plugins activés de l'utilisateur (`~/.claude/settings.json`, ou `$CLAUDE_CONFIG_DIR`) et du projet sont à `false` (`enabledPlugins`), sauf `cadence` et `playwright` ; les connecteurs du compte claude.ai sont coupés (`disableClaudeAiConnectors`), les serveurs MCP des plugins restent ; la mémoire auto est désactivée (`autoMemoryEnabled: false`). Premier tour : 64 844 → 57 653 jetons (−11 %), environ 0,12 $ par lot. Les autres réglages de l'utilisateur et du projet s'appliquent comme avant. Le banc ne prend pas ces coupes : ses bras gardent leurs réglages, et le bras `cadence run` du banc n'est donc plus tout à fait le run.

Le `CLAUDE.md` du dossier parent du dépôt est chargé parce que le worktree est sous `../.cadence-run/` (5,3 k jetons sur Big-Blue). Un dépôt qui n'en a pas besoin le coupe dans son `cadence.yaml` :

```yaml
run:
  worktreeOutside: true   # défaut false : le CLAUDE.md parent peut porter des consignes de sécurité (maritime-atlas : kubectl pointe sur la prod)
```

Le worktree va alors sous `$CADENCE_HOME/run-worktrees/<projet>-<id>` (défaut `~/.cadence/orchestrate/run-worktrees/`) ; l'état, le verrou et le journal restent dans `../.cadence-run/`. Une autre valeur que `true` ou `false` est refusée avant toute création.

En cas d'échec, le worktree est gardé avec l'état du run (`../.cadence-run/<projet>-<id>.json`). Le run s'arrête alors dans l'un de ces états : `sans-commit`, `conflit`, `porte-rouge`, `sans-porte` ou `refus-integration`.

## Pourquoi ces options

| Option | Justification |
|---|---|
| `--piece` | Le hook « lecture obligatoire » est le seul gain clairement prouvé au banc séquence (lecture des références). La pièce est la liste qu'il fait respecter. |
| `--taille` | Le brief mesuré reçoit la taille du gardien. Sans gardien, la valeur par défaut est `fonction`, comme au banc court. |
| `--reponse` | Une question à Sylvain reprend la même session (cause C2 : ne pas découper le contexte). |
| `--liste` | Retrouver un run rendu, en attente, rouge ou interrompu (L709), sans fouiller le disque. |
| `--inactif` | Le seuil du signalement « session bloquée ? » de `--liste` (L763, issue #63 : deux runs bloqués 21 et 55 min le 17-11), 15 min par défaut. |
| `--complet` | Forcer le mode complet quand l'aiguillage rate une demande qui a des références. |
| `--lot` | Les commits d'un dépôt suivi par un plan citent le lot (`feat(L51): …`) : la session le reçoit avec la demande. |
| `--demande-humaine`, `--registre` | Le registre ne garde que les demandes de l'humain : sans l'une des deux, le run est une consigne du lead et n'y écrit rien (L701 ; huit consignes inscrites à tort les 10 et 11-11). |
| `--modele`, `CADENCE_RUN_MODELE` | Choisir le modèle de la session : `opus` (défaut, celui des deux bras mesurés au banc) ou `fable` ; Sonnet et Haiku n'écrivent pas de code (cause C2). La valeur s'écrit en minuscules. L'option l'emporte sur la variable ; une valeur inconnue est refusée en code 2 avant toute création ; la ligne de lancement dit le modèle utilisé et d'où il vient (L699, L726). En Fable, le run sort de ce que le banc a mesuré ; Fable s'impose seul à la 3e passe de correction du lot ou après deux revues non conformes (L726, ci-dessus). |
| `--fond` | Le run se détache et survit à la session qui l'a lancée (vécu au compte pro le 10-11 : un lot mort avec la session précédente, puis deux runs le 11-11, issue #55) ; journal dans `../.cadence-run/`. Ses sessions ne gardent aucun lien avec la session lanceuse (L709). Le journal dit qui était le run et ce qui l'a arrêté (L711). |
| `KUBECONFIG` | Comme les vagues : sans `orchestrate.prodAccess: true`, la session n'a ni `kubectl`, ni `helm`, ni `KUBECONFIG` ; avec, elle joue le banc du projet. |
| `run.worktreeOutside` | Couper le `CLAUDE.md` parent (−5,3 k jetons au premier tour, mesuré le 12-11), dépôt par dépôt : il porte parfois des consignes de sécurité, d'où le défaut `false` (L705). |
| `--purger`, `run.purgeAfterDays` | Le dossier des runs grossit sans fin (51 dossiers de captures, 174 états le 17-11) : retirer les fichiers des runs finis depuis N jours, jamais ceux d'un run qui se reprend ou dont le worktree est gardé ; `--dry-run` pour lister d'abord (L767). |
| `--sans-porte` | Un dépôt sans porte déclarée n'est pas intégré en silence : il faut le choisir explicitement. |
| `--help`, `-h` | L'usage, sans rien créer (issue #54 : « --help » partait en demande, laissait worktree, branche et état). Un autre argument qui commence par `-` est refusé en code 2 avant toute création. |

## Mesures qui le fondent

- Bras v2b (une session, sans relecture), préféré à v2 (avec relecture) : environ ×1,4 plus rapide.
- Registre des demandes (v2d) : la demande différée est tenue 3 fois sur 3 avec registre, 0 sur 3 sans, pour +7 % de temps (micro-banc, 09-11).
- Hook « lecture obligatoire » : les références sont lues en entier.
