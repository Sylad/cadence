### Fixed

- `cadence run --liste` no longer shows a run as `conflit` (or `refus-integration`, `porte-rouge`…) once all its commits are on the target branch, merged or replayed by hand: it shows `integre a la main`, checked with `git cherry` against the run's branch, or against its head saved in the run state when the branch is gone. The new `cadence run --clore <id>` then removes the run's worktree and branch and marks it closed in its state; it refuses, saying why, while a commit of the run is missing from the target, while the run can still be resumed, or when its worktree has uncommitted changes (L745, issue #62, [docs/v2/2026-11-09-cadence-run.md](docs/v2/2026-11-09-cadence-run.md)).
- `cadence run --liste` and `--clore` also recognize a `conflit` run integrated by hand with a conflict resolution (cherry-pick or rebase, different patch-id) when every file the run changes has the content of the run's head on the target. When the resolution differs, `--clore` names the differing files and points to the new `cadence run --clore <id> --force`, which closes the run without proof of integration, prints its head, and shows as `clos … par --force` in `--liste` (L745 review).
- `cadence run --reponse` refuses a run closed by `--clore` instead of starting a session on its removed worktree and rewriting its state to `echec` (L745 review).
- The content check of `cadence run --liste` and `--clore` no longer reports a run as integrated when one of its files is missing from the target and has an accented name (`décision.md`), a leading `:` or a `\` (`a\b.txt`): file names are read with `git diff -z` and compared in JS instead of being passed back to git as pathspecs, and a failing `git diff` now means not integrated. Before, `--clore` exited 0 and deleted the run's branch (L745 second review).
