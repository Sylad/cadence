# orchestrate — the gate

The program's own gate (build, tests, red at the start, replay alone, `readsPlan`), the pre-check of shared files and the edge-case probe. The five pages of `cadence orchestrate`: [commands and options](orchestrate.md) · [the cycle of a lot](orchestrate-cycle.md) · **the gate** · [spec, mockup, accept, briefs](orchestrate-spec.md) · [worktrees, neighbours](orchestrate-worktrees.md).

**A project without `orchestrate.test` is flagged (L327)**: without the key the wave never runs the suite itself — only the review does, if it decides to (it ran 12 test files of a project on 2026-10-25 and a red test reached « ready »). `cadence orchestrate --dry-run` writes one line per repository, under the first lot of that repository: `<repo> · porte de tests absente : orchestrate.test n'est pas déclaré, la vague ne lancera pas la suite (seule la revue le fera si elle le décide) · commande probable : npm test (à déclarer en orchestrate.test)`, and [`cadence lead tour`](lead.md#lead-tour) writes the same line for every project of the folder. The probable command is read from the repository, never run: `npm test` when `package.json` has a `scripts.test` (the `npm init` placeholder « no test specified » does not count), `pytest` when `pyproject.toml` names pytest, `mvn test` when there is a `pom.xml`; with none of them the line carries no command. A `cadence.yaml` that cannot be read gives no such line (it has its own error). Declaring `test:` (and `build:`) in the project's `cadence.yaml`, once the command is known to be green, removes the line.

**A test the CI plays and the gate does not is flagged (L499)**: on 17→31-10, 37 deliveries went red for ~12 h, some on tests played only in CI (warhammer's e2e). `cadence orchestrate --dry-run` reads the repository's `.github/workflows/*.yml|yaml` (the `run:` steps of every job, multi-line, chained with `&&`, `;`, `|`, `\` continuations; `npm|pnpm|yarn test` and `run <script>` are unfolded through the `package.json` of the step's `working-directory`, even behind environment variables or a wrapper (`CI=true npm test`, `DEBUG=pw:api npm run test:e2e -- …`, `npm test --silent`; `--silent` (or `--silent=true`), `--if-present`, `--quiet`, `--loglevel=silent`, `-s` and `-q` are skipped, `--workspace` and `--prefix` are not), followed through `cd`, including in `( … )` subshells, where the `cd` ends at the closing parenthesis; `&&`, `;` and `|` inside quotes do not split; `xvfb-run`, `timeout`, `time`, `env`, `nice` and quoted environment variables are stripped; `python -m pytest` is `pytest`, `mvn -B test` is `mvn test`) and, once per repository, writes `  ⚠ <repo> · parité porte ↔ CI : la CI (<workflow>) joue « <command> », que orchestrate.test et orchestrate.build ne jouent pas …` for each test command (vitest, jest, mocha, playwright test, cypress run, pytest, mvn test, go test, cargo test, ng test/e2e…) that `orchestrate.test` (each part in its own `dir`) and `orchestrate.build` do not play. Two commands are the same when they differ only by environment variables, `npx`, redirections (`2>&1 | tee log`, `> out.log`, `2>/dev/null`, which do not split the command either) and options (`--coverage`); a file, a configuration (`-c`, `--config`) or a project (`--project`, `--selectProjects`, `-p`) argument makes another command. Nothing is written without workflows, without `orchestrate.test` and `orchestrate.build` (`porte de tests absente` says it), or with an unreadable `cadence.yaml`. `cadence lead tour` and `cadence verify --gate` write the same line (`docs/lead.md`, `docs/deliver.md`); nothing is changed in the gate itself, the line only tells what its green does not cover.

**Tests already red at the start (L213)**: a lot is no longer handed back « tests rouges » for failures that were there before it. When `orchestrate.test` fails (or the session reports red tests), the program reads the failing tests from the runner's output (vitest/jest `FAIL`/`●`, pytest `FAILED`, go `--- FAIL:`, TAP `not ok`), replays the same command at the sha the lot started from (the parent of the lot's oldest work commit, plan-only commits left out, else the `HEAD` before its first session) in a throwaway `git worktree` outside the repository, and compares: if every failing test was already red, it is not a defect of the lot — no correction pass, the code review takes place, the reviewer is told, and the final table lists them apart (`déjà rouge au départ (<sha>) : <test>`, 30 at most then a count). The worktree gets links to the repository's ignored folders at any depth, such as `.venv` and, in a monorepo, `packages/*/node_modules`, when their parent exists at that sha; build outputs such as `dist` or `coverage` are left out. Each `node_modules` is rebuilt entry by entry, every entry linked to the live one except the workspace links of npm, pnpm and yarn (`node_modules/@x/shared -> ../../packages/shared`, a link to code of the repository outside any `node_modules`), which are remade towards the worktree's own copy so that the start sha is tested against its own sources, not the lot's (a workspace package that does not exist at the start sha gets no link). Known limit: only `node_modules` links are remade; whatever points into the live repository by an absolute path, such as an editable Python install (`.venv` with a `.pth` file naming the live `src`, `pip install -e`) or an absolute symlink in another ignored folder, still runs the lot's code in the baseline. Likewise, a workspace package consumed through its build output (`main: dist/...`) cannot load in the baseline worktree: output dirs are not linked, so such a monorepo keeps the pre-L213 « tests rouges » outcome unless `orchestrate.build` is declared (the build is then played first in the baseline worktree, see below). A lot resumed in a later wave keeps the same baseline: the sha is the parent of its oldest work commit, not the `HEAD` of the new wave, so a failure the lot itself introduced in an earlier wave is never excused. A test red now and not at the start stays a blocking finding, and only that one is given to the correction (the others are counted as « already red »). When the output names no test, or the baseline cannot be run, the tests stay red as before (no comparison is guessed). A failure the output does not tie to a test (unhandled error, a spec file that fails to load such as jest « Test suite failed to run » or vitest `FAIL  a.test.ts [ a.test.ts ]`, coverage threshold) keeps the tests red. Without `orchestrate.test` the program cannot replay anything: a session that reports green tests and lists under `echecsDeBase` the failures it saw at the start sha gets them listed apart, marked « non vérifié » in the table, and the review takes place; a session that reports the tests red stays red, the brief asking it not to report red for base failures alone — unless (L215) the report says so in a structured way: with `vert: false`, a non-empty `echecsDeBase` and an empty `nouveauxEchecs` (the list of tests red now that were not red at the start sha), `vert: false` is not a reason to correct, the lot carries a « non vérifié » warning, the reviewer is told that the baseline is unverified and the review takes place. A non-empty `nouveauxEchecs` with `vert: false` triggers a correction pass (the new failures are in the finding); an absent `nouveauxEchecs`, or an empty `echecsDeBase`, keeps the correction. With `orchestrate.test` declared, when the program's own gate is green (`orchestrate.test` exits 0, L361; made unconditional by L522) the claim of red tests is never believed, whatever `echecsDeBase` and `nouveauxEchecs` hold (absent, empty or not, a non-empty `nouveauxEchecs` included): one warning (`tests annoncés rouges par la session, mais la porte du programme verte (<command>, code 0) : l'annonce n'est pas crue, pas de correction`), the review takes place, no correction pass and no « tests rouges » escalation. A red gate (non-zero exit) keeps the rules above. The program never guesses from the text of the result (« 24 failed »). The `implement` and `fix` briefs ask for `echecsDeBase` and `nouveauxEchecs`.

**A config key set before its service install is refused (L504)**: on 31-10 L497 turned on `orchestrate.probe` in cadence's own `cadence.yaml` while the installed copy (the one that plays the wave) did not know the key: every cadence command on the repository then failed, and the integration of L480 died on the way. When a lot modified the `cadence.yaml` of its repository, the program's gate (before `orchestrate.build`, after a writing session and at the rebased tip) reads it with the loaders of the installed copy (`validateConfig`); a refusal is a blocking finding (`cadence.yaml refusé par la copie en service de cadence (…)`) sent to correction without playing the build or the tests. The key is set in a lot that follows `npm run service`. A `cadence.yaml` the lot did not touch is not read (a config already broken at the start is not its defect). **`--resume --integrate` and an unreadable config**: the repository's `cadence.yaml` of every lot named by `--integrate`/`--replay` is read before anything is written (a lot resumed by `--budget` or `--answer` keeps the error raised by `execute`); an error is a refusal (exit 2) that leaves the lot `handed-back` and the wave `done`. A lot an earlier resume left `suspended` at the `integrate` step in a wave that is `done` (the state before this check) is taken back by `--resume --integrate`; in a wave that is not `done`, it stays refused.

**The build is played before the tests (L333)**: the gate of the wave runs `orchestrate.build` first, then `orchestrate.test`, because tests that read the build output (end-to-end tests over `dist`) are red without it — on 2026-10-25 three projects had to declare `test: astro build && npm test` (13 tests out of 15 red without `dist`), which played the build twice on every pass. A red build hands the lot back as a single « build » finding and the tests are not run. The L213 baseline plays the build first in its throwaway worktree too, then the tests: without it the start sha, with no `dist`, would excuse a test wrongly or turn everything red. A build that fails at the start sha gives no baseline (the build says nothing about the tests there): the tests stay red as before, no comparison is guessed. Without `orchestrate.build` nothing changes. A project that wrote `build && test` into its `orchestrate.test` can drop the duplicate build.

**The free machine first: `orchestrate.gate.overflow` (L639)**: `gate.host` keeps its meaning (the gate is played on the host); `gate.overflow` instead plays the gate locally when no local gate holds the machine and overflows to that host when it is busy, deciding once per lot whether the host answers (ssh `ConnectTimeout=3`), and falling back to the local turn without repeating the line or the timeout; it is refused together with `host`. Details: [remote-gate.md](remote-gate.md#the-free-machine-first-gateoverflow-l639).

**The program's gate is a visible step (L395)**: while `orchestrate.build` or `orchestrate.test` runs (after a writing session, at the rebased tip, and for the replay that follows a red), no claude session runs, and the lot used to read `implémentation` in `--status` and `→ implement` in the `cadence-hud` band: on 28-10 the gate of L392 ran 5 silent minutes. The lot's state now carries `gate` (`build` or `tests`, with its start), set when the command starts and removed when the checks end, red or green. `--status` prints the state `porte tests (3 min)` instead of `implémentation` (only for a running wave: a `gate` left in the state of a killed wave is not shown as running), and the band prints `porte@tests 3 min` where it printed `→ implement`. `--status --wave <wave>` is the same as `--status <wave>` (it used to show the last wave of the folder); two different ids are refused. **A gate played on `orchestrate.gate.host` frees the pool's slot (L624)**: the lot's state then carries `gate.remote`, the pool counts no queue for it and starts the next one; the host's own bound is `gate.maxParallel` (2 by default), and a gate waiting for that bound frees the slot too, its state carrying `gate.waiting` and `--status` printing `porte en attente de l'hôte (3 min)`, see [remote-gate.md](remote-gate.md).

**No correction pass without a finding, and a red that passes alone is proposed, not corrected (L522)**: the study of L517 classified 580 correction passes of the waves of 2026-10-23 to 2026-11-01: 73 were « sans-constat » (13 %), and 48 of those 73 ended with no commit. Two causes are closed. (1) A non-conforme review, code or UX, that lists no actionable finding no longer opens a fix pass: a finding is actionable when it is blocking or major and its text, trimmed, is not empty (minors never are, on this path); the review can announce `bloquants: 1` with `constats: []`, and `conforme` is false on the announced totals. The lot is handed back (`handed-back`) with the cause `revue non conforme sans constat actionnable (N bloquant(s), M majeur(s) annoncé(s), aucun constat lisible) : pas de passe de correction` in the table and in the wave log; `pass` is left as it was, `next` is cleared (never `fix`: the lot is handed back) and the lot's findings are emptied, so a resume does not reopen the pass. A conforme review is untouched (minors pass, proposals). (2) A test red in the whole suite, absent from the baseline and green when replayed alone (the replay of L354, which needs `orchestrate.testReplay`) is still noted unstable as before (warning, wave log, `instables`) and now adds one lot proposal, `[instable] <test> — rouge dans la suite, vert rejoué seul : à stabiliser`, once per test; a « délai trop juste » test (L510) keeps its own warning and adds no proposal. The `fix` brief asks the session to replay each red test it is given alone before writing code, to leave a test that is green alone untouched and to list it under `choix` as unstable. **Measure**: the before/after reading is the `sans-constat` row of `cadence corrections` read by `node scripts/temps-d-un-lot.mjs --corrections <corrections.json>` (L517, unchanged by this lot): start of the window, 73 passes out of 580 classified (13 %), 48 of those 73 finished without a commit. The row also counts the passes opened on red tests with no review, so the drop expected after this lot is the unstable reds and the announced reds (L361 rule above), not the real red tests.

**A red test is replayed alone before it counts, only on a declared command (L354)**: on 2026-10-26, with 32 cores and a cap of 4 sessions, every suite ran vitest at 31 workers, and four correction passes (L344 11 min, L342 9, L349 7, B28.12 4) found nothing to fix — each time « a test that passes alone ». cadence does not guess how a file is replayed on your runner (a first version appended the files to `orchestrate.test` and, on a composed gate, excused a real regression), so the replay is **off unless the project declares its command**: `orchestrate.testReplay`, where `{files}` is replaced by the files of the red tests, e.g. `testReplay: "npx vitest run --maxWorkers=$CADENCE_TEST_WORKERS --minWorkers=1 {files}"` (a value without `{files}` is refused when the file is read). **Without it nothing is replayed and nothing is held for unstable**: a red test is counted as before. With it, a red test of the gate (`orchestrate.test`, played after every writing session and at the rebased tip) that is absent from the baseline is **replayed alone, twice at most**, by that command, in the lot's worktree (vitest names `file > suite > test`, pytest `file::test`, jest `FAIL file` and `● Suite › test`, the latter tied to the `FAIL` line that precedes it in the same output and replayed with that file; the file is the part before the first `::` or ` > `, so either of them inside a test title is not part of the path). Green at a replay, the test is **« instable sous charge »**: it is not counted, it triggers no correction pass, even when the session reported its tests red (`vert: false`: a session that plays the suite under the same load sees the same red; the announcement is not held against the lot when every red of the gate is unstable, as it is not when every red was already red at the start), the lot goes on to its review, and the trace is a lot warning (so a line of the final table), a journal line `<project>:<lot> · N test(s) instable(s) sous charge …`, the lot's `instables` list in its journal, and the `cadence perf` line `tests instables sous charge` (`instables` in `--json`). Red at both replays it is counted as before. A red name that designates no file (a plain `FAIL name`) cannot be replayed alone and is counted at once. **A replay in which the test did not run counts red**: only a replay that exits 0 after running tests proves a test green, and only for the tests whose file appears in the replay's output, as a whole path on a line of the runner — never in the launcher's echo of the command: npm 12 writes `npm notice run 'vitest' run … <files>` on stderr for `npx …` as for `npm test -- …`, npm and pnpm write `> vitest run … <files>`, yarn `$ …`, and those lines name every file asked for, played or not (a runner that silently skips a file it cannot find, such as vitest given a path of another workspace, exits 0 without playing it: that test stays red; with a reporter that does not list files, nothing is ever excused; `a.test.ts` is not found in `src/a.test.ts`); a replay that fails, or that runs no test (the runner's closing line `No test files found, exiting with code`, `No tests found, exiting with code` or `no tests ran in`, even with exit code 0; the same words inside a test title or a test's output do not count), leaves every test it was asked about red. In a vitest workspace the names read `|package|  src/a.test.ts > case`: the `|package|` prefix is dropped to find the file. The reviewer is told which tests were red under load (`instables` of the check, also when the baseline holds red tests of its own), so it does not report them, and the correction finding lists only the tests still red after the replays. The baseline run is included: with `testReplay`, a red test of the L213 baseline (the gate played at the start sha, in its throwaway worktree) is replayed alone there, twice at most, before it is retained as « already red at the start »; green at a replay it is dropped from the baseline (a journal line `… · ligne de base <sha> : N test(s) rouge(s) sous charge, vert(s) rejoué(s) seul(s), non retenu(s) …`), so a test the lot really breaks is not excused by a load failure of the start sha. The baseline replays are not the lot's « instables »: they say nothing about the lot's code. **A composed gate is not supported (decision of 26-10)**: `orchestrate.testReplay` is refused when `cadence.yaml` is read if `orchestrate.test` has `&&` or `||` outside quotes, or a parenthesis (sub-shell `( … )`, `$( … )`, function): a first runner that goes red cuts the next one, so a green replay of its tests says nothing of the rest, and a replay command written for one runner of the gate cannot replay the tests of the other. Write the replay for a gate that launches a single runner; without `testReplay` a composed gate is played as before, nothing is replayed. A jest `FAIL` line may carry a duration (`FAIL src/a.test.ts (6.21 s)`) or a project name (`FAIL backend src/a.test.ts`): the file is its last word, and any other `PASS`/`FAIL` line ties no file to the `●` lines that follow. The `FAIL project file` line is itself a red name (`project  file`) and is replayed with that file, like the `●` tests under it.

**A test that expires close to its limit even alone is a « délai trop juste », not a bug (L510)**: on 2026-10-31 a test of warhammer (L61) took 25 s alone for a 30 s delay: it passed alone, expired under the slightest load, and the gate sent four correction passes and the escalation for a defect that was not one. A composed gate declares its parts (`orchestrate.test` as a list, L512, below) to get the same. The replay alone now also reads the **duration** of the test (its own line `✓ file > test 25012ms`, else the `✓ file (3 tests) 24s` line of its file, an upper bound) and the **delay** it expired at in the whole-suite output (vitest `Test timed out in 30000ms`, jest `Exceeded timeout of 5000 ms for a test`). Green alone at **80 %** of that delay or more, the test is no longer filed with the unstable-under-load ones: no correction pass, the lot's `delaisJustes` (test, duration, delay) and a warning that names it (`délai trop juste, pas un bug … : test/a.test.ts > plan-data (25 s seul pour 30 s de délai) — relever le délai du test`), shown in the end-of-wave table. A test still red alone is a bug whatever its delay; a test with no delay in the suite output or no readable duration stays an ordinary unstable test.

**A red already red at the baseline triggers neither a correction nor the escalation (L510)**: on 2026-10-31 evatosorus L45 got a Fable correction on the drawer test of L23, a test that was red before the lot. A composed gate declares its parts (`orchestrate.test` as a list, L512, below); `node --test` (evatosorus) is covered by L514, below. The baseline (L213) is one run of the whole suite, replayed alone for what it sees red (L354); a test that run did not see red (order, load, state left by another test) but that is red **alone** at the start sha was not excused. With `orchestrate.testReplay`, a test still red after its replays alone in the lot is now replayed alone at the start sha too (a throwaway worktree, the build first): named as failing by two replays that exit in failure, it is already red: `dejaRouges` on the gate run, a warning that names it, no correction pass and no escalation for it. A replay at the start sha that fails without naming the test (another test red, a build that does not run) excuses nothing; a test with no file to replay alone is never excused; without `testReplay` nothing is replayed at the start and the red counts as before. When other tests of the same run are new reds, only those are sent to the correction.

**A gate declared in parts: each part runs in its folder, each red is replayed by the part that printed it (L512)**: on 2026-10-31 the gate of warhammer was `(cd backend && npm test) && (cd frontend && npx vitest run …)`, a composed gate for which `testReplay` is refused, so neither the replay alone (L354) nor the « délai trop juste » and « déjà rouge » of L510 applied: four correction passes and an escalation for false reds (L61). `orchestrate.test` now also takes a **list of parts**, `[{ dir, run, replay? }]`: `dir` is the folder the part runs in (relative to the repository, no `..`, unique), `run` its command, `replay` (optional) its replay-alone command, with `{files}`. cadence runs **every part separately, in its folder** (`cd <dir> && <run>`, on the host of `gate.host` too), all of them even when one is red (a `&&` stops at the first red and hides the next parts), and **attributes each red test to the part whose output printed it**: no reading of a shell chain, no path prefix, no disk access. A red of a part that declares `replay` is replayed alone by that command, in that folder, with the files that part printed (twice at most; the L354 and L510 rules are unchanged: exit 0 with the file on a line of the runner, duration against the delay, replay alone at the start sha, baseline included); a part without `replay` keeps its reds counted as before, and so does a name that designates no file. **A name printed red by several parts is replayed in each of them and is green only if every one of those replays is green** (a part without `replay` can never clear it): never a false green. The string form of `orchestrate.test` is accepted unchanged (one block; `testReplay` still refused on a composed chain); `testReplay` next to a list is refused (declare `replay` in each part); a part whose folder does not exist makes the gate red (`can't cd to <dir>`) and nothing is replayed — more generally **a red part that names no test** (compile error, crashed runner, `cd` failure) **or whose output carries an unnamed failure** (coverage threshold, a file that does not load) blocks every replay: the gate stays red even when the named reds of another part pass alone, as a string gate does on an unnamed failure. At the baseline (start sha), where the replay alone *removes* excuses, each part is still judged on its own: a part red without a named test there withholds only its own reds (none), and the load reds of the other parts are replayed by their part and dropped, so a real regression of the lot is never « déjà rouge ». Wherever the gate is shown, a list reads `dir : run ; dir : run` — the lot's check run and the cache key of its baseline (which `cadence verify --gate` compares to take over a wave's verdict), the `tests` step of `verify --gate` (which also names the red parts), the accept session's prompt, the green-gate warning — and the implement, fix, probe, minors and librarian briefs give one `tests (run in \`dir/\`)` line per part. warhammer declares:

```yaml
orchestrate:
  test:
    - { dir: backend, run: npm test }
    - { dir: frontend, run: "npx vitest run --exclude '**/*.e2e.spec.ts'", replay: "npx vitest run --minWorkers=1 --maxWorkers=$CADENCE_TEST_WORKERS {files}" }
```

**`node --test` (evatosorus) is replayed alone too (L514)**: that runner names a red test by its title only (`not ok 3 - the drawer opens`), never by its file, so the title alone designates nothing to replay. cadence now reads the file in the `location: '/path/a.test.mjs:12:3'` line of the YAML block that follows the `not ok` line (line and column dropped), and replays that file with the part's `replay` (`{files}`). A passing test prints no file, so the proof that the replay ran it is its own `ok N - <title>` line (exact title, not `# SKIP`, not `# TODO`) in a replay that exits 0: a replay that exits 0 without that line (no test found, test skipped) leaves the test red. A red with no `location:` (old Node) or a title red in two different files (the replay of one file would say nothing of the other) has no file: it is never replayed and stays counted. At the start sha (L510) the file is replayed relative to the folder where the lot's gate ran, never by its absolute path, which would replay the lot's own copy of the test: a path inside the lot's worktree is made relative to the part's folder, even when it leaves it (evatosorus runs from `frontend/` and its tests live in `scripts/`: `node --test ../scripts/drawer-keyboard.e2e.test.mjs`); a path outside the lot's worktree (a gate played on `gate.host`) designates nothing to replay and the test is never excused. The other runners are unchanged (`failedTests`, the file read from the name or from jest's `FAIL` line, the file printed by the runner). evatosorus runs its tests from `frontend/` (`cd frontend && npm run test:scripts`, a composed gate that refuses `testReplay`), so its gate is declared in parts to benefit from it:

```yaml
orchestrate:
  test:
    - { dir: frontend, run: npm run test:scripts, replay: "node --test {files}" }
```

**Each session gets its share of the machine (L350)**: the wave computes `CADENCE_TEST_WORKERS = max(1, cores ÷ session cap)` (`--max-sessions` or `CADENCE_MAX_SESSIONS`; 32 cores and a cap of 4 give 8; a `CADENCE_TEST_WORKERS` already set in the environment that launches the wave wins when it is a positive integer). It is put in the environment of every session and of every command of the gate (tests, build, baseline, replays), recorded as `testWorkers` in the wave state, and the `implement`, `fix`, minors and librarian briefs tell the session to respect it: `vitest run --minWorkers=1 --maxWorkers=$CADENCE_TEST_WORKERS` (vitest 2 refuses `--maxWorkers` alone, its default minimum being the core count: « options.minThreads and options.maxThreads must not conflict »), `jest --maxWorkers=$CADENCE_TEST_WORKERS`, `pytest -n $CADENCE_TEST_WORKERS`. The gate command itself must honour it for the share to bind: cadence's own `vitest.config.ts` reads it (`poolOptions.forks.maxForks`, `threads.maxThreads`); in another project write `orchestrate.test: npx vitest run --minWorkers=1 --maxWorkers=$CADENCE_TEST_WORKERS` (or the equivalent of its runner).

**The session plays the gate's own commands (L399)**: the briefs of the writing sessions (implement, fix, minors pass, librarian pass) name the exact `orchestrate.test` and `orchestrate.build` of the project (`The program's gate, played by the program after your writing session, is exactly: …`) and ask to run the build as written, not a narrower equivalent (the tests are targeted since L518, below). Measured on 22–28-10 (`docs/mesures/portes-rouges-2026-10-28.md`): sessions that played `npm run build` (`src` only) announced a green lot that `npx tsc --noEmit` (tests included) sent back to a correction pass. Without `orchestrate.test` and `orchestrate.build` there is no line.

**One full gate per lot (L518)**: the writing sessions no longer replay the full suite. Measured by `scripts/temps-d-un-lot.mjs` (study L517, `docs/mesures/temps-d-un-lot.md`): 1 945 full suites played inside the sessions (2.7 per lot, median 2, 1.8 min each) on top of the 1 337 the gate plays after the writing sessions; one UI separator (ol L239) replayed the suite 5 times. The briefs (implement, fix, minors pass, librarian pass) now say: play only the tests of the code you touch (targeted, once, before committing) and the build as written; the full suite is the program's gate, played once by the program (after the session for a lot without worktree; at integration for a lot in a worktree, whose gates after a write are targeted since L590, below), and `cadence verify --gate` takes its verdict back (L397) instead of playing it again. The `{{gate}}` text carries this when the project declares `orchestrate.test`; with `orchestrate.build` alone the text lists the build and tells the session to play the full suite itself, once (the program plays no suite then); with no gate declared the briefs tell the session to play the full suite itself, once, since nobody else will. The wave measures it: the `suites` column of the final table (and of `--status`) is the number of times the program played the full `orchestrate.test` for the lot (`suiteRuns` in the lot state: one per full suite played (a writing pass without worktree, the integration with one), replays alone of red tests not counted; `—` when none was played, a gate without `orchestrate.test` or a state written before L518). The suites a session plays itself stay measured by `scripts/temps-d-un-lot.mjs` from the transcripts (the program does not read them), so the table shows the gate's share only: with the briefs followed, a lot of one writing session reads `1`.

**Targeted gates after a write, the full suite once at integration (L590)**: on 2026-11-04, 61 lots of 03 and 04-11 played 271 suites (4.4 per lot), and the 2 119 minutes between sessions weighed 59 % of the 1 469 minutes of sessions (upper bound: it includes the wait for a slot). After a write (`implement`, `fix`, the probe) the gate now plays only the tests related to the files of the diff between the lot's start sha and `HEAD` (deleted files left out): the command is `orchestrate.testRelated` (a string that contains `{files}`, replaced by those files, each quoted for the shell), or, when it is absent, derived from an `orchestrate.test` that is a simple string `[npx ]vitest run[ options]` into `[npx ]vitest related --run[ options] {files}` (`npx vitest run` gives `npx vitest related --run <files>`); every option starts with `-` (`--reporter=dot`, `--maxWorkers=$N`). Any other form (`npm test`, a workspace runner, `a && b`, a sub-shell, a list of parts, a positional filter such as `vitest run test/unit` or an option with a separate value such as `--reporter dot`) derives nothing: kept in `vitest related --run … <files>`, that filter would become one more « related » file and the gate would play the tests the filter leaves out, absent from the baseline: the full suite is played at every gate, as before, unless `testRelated` is declared; `testRelated` is refused without `{files}` and with `orchestrate.test` as a list of parts, and accepted with a composed `orchestrate.test` (then the only one played in a targeted gate). A targeted gate whose command finds no test (the launcher's end line, `No test files found, exiting with code 0` for vitest, the same detection as the replay alone, exit code 0) plays the full suite instead and records the reason « aucun test lié »; with no start sha, or an empty or unreadable diff, the full suite is played too. A red targeted gate takes the path of a red full suite: baseline at the start sha (the full suite, once), replay alone, unstable, already red, then the finding to correct. The build is played at every gate, as before. At integration the full suite is played **once per tip**, rebased or not, unless `checks` already holds a green full suite for the tip's tree (the fallback above): a replayed rebase changes the tip, so it plays the suite again, and a red full suite at the integrated tip is rerun once, then refuses the integration, as before (L328). A targeted run is recorded in `checks` with the related command and `portee: ciblee`: `cadence verify --gate` never takes it for the verdict of the suite, and the review brief says that only the tests related to the lot's files were played and that the program plays the full suite at integration. Each test gate, targeted or full, adds an entry `{ portee, fichiers, code, duree (seconds), motif? }` to `portes` in the lot state (absent in a state written before L590: read as an empty list); `suiteRuns` stays the number of **full** suites, so the `suites` column of the table is unchanged, and `cadence orchestrate --status --detail <lot>` (and the final table) lists one line per gate: kind, number of files (targeted), code, duration. When the session reports red tests (`vert: false`), the gate of that write is played as the full suite, not targeted: the announced test is not necessarily related to the diff, and only the full suite has the baseline and the verdict that L213 and L522 compare the announcement to. A lot concluded by the express route records its gate in `checks` like any other, so the integration does not replay a green full suite for the same tree. A lot that touches `CHANGELOG.md` also plays `test/changelog.test.ts` in its targeted gate when the repository has that file (L616): no test imports the changelog (it reads it), so `vitest related` never found it, and three refusals of 05-11 (L582, L591, L613) for an entry written under the last published version instead of `[Unreleased]` were seen only at the integrated tip; the `{{gate}}` text of the briefs says it. Limits: a diff that touches only files no test imports (docs, `cadence.yaml`, templates) falls back to the full suite, with no gain; a lot with no worktree (`orchestrate.worktrees` false, the default; a single lot in a single slot; a multi-repository lot `repos:`) has no integration to play the full suite, so its gates stay full as before L590, never targeted; the express route (L519) concludes on the program's gate, now a targeted one, the lead reading the diff.

## Sealed tests and shared files: the pre-check of what a lot may collide with (L500)

On 17 → 31 October, 19 of the 43 questions of the sessions were about a sealed acceptance test of another lot (median block: 56 min) and 16 of the 28 refused integrations were conflicts. Both are known before the first line of code, so the program reads them from git, with no model and no key to set.

**When.** Once, at the start of a lot that is not resumed from a kept branch (`resumedFrom`), whether or not the model pre-check (`orchestrate.precheck`) plays, and whatever the size of the lot (`light` and `small` lots play it too, L628: it reads git and costs nothing).

**What it reads.** The files the lot may touch are the tracked files its text cites: title, `goal`, notes and sub-tasks. A path is matched exactly (`src/x.ts`, with `:line`, a final punctuation mark or a leading `./` ignored); a bare file name is matched only when one tracked file has that name. A directory or a glob names nothing. From those files:

- **Sealed tests of another lot**: every `acceptation-<lot>.json` under `spec.dir`, of another lot and with fingerprints (`empreintes`, so sealed), whose test files or sheet (`fiche`) are among them, **or whose test files import one of them** (L628: a lot that changes a delivered behaviour cites the code, rarely the test that freezes it; the import is read in the test at `HEAD`, relative specifiers only, `.js`/`.ts` ignored, one line per test with the first cited file in `via`). The lot's own acceptation is never listed.
- **Shared files**: the files that the branch of another lot with a worktree (a wave still alive, this one included, or a worktree kept after a wave, `cadence orchestrate --status`) modified since its start (`base...branch`, unintegrated commits only). The lot's own branch of a past wave is left out.

**Where it shows.** In the `partage` field of the lot's state; in the brief of the implement step (first and later passes): the sealed tests to leave alone, with the lot that seals them and the instruction to stop and ask the lead if the lot's own tests contradict one (for a test that only imports cited code: stop, and put under `questions` the reseal gesture, `cadence spec reseal <lot> <test>… --reason … --porteur <lot>`, instead of editing the test and being handed back at the commit), then the shared files with the lot that touches them; and in the table (`--status`, end of wave), one line per test and per file:

```
demo:L500 — ⚠ test scellé de L10 que le lot risque de toucher : test/a.test.ts (docs/specs/ecran/acceptation-L10.json)
demo:L500 — ⚠ test scellé de L10 que le lot risque de toucher : test/b.test.ts (docs/specs/ecran/acceptation-L10.json), il importe src/x.ts
demo:L500 — ⚠ fichier que touche aussi demo:L1 (vague en cours) : src/x.ts
```

**Limits.** It lists what the lot's text names: a lot that cites no file gets no line, and a file it will touch without naming it is not seen. Only the lot's own repository is read (not the neighbouring ones of `repos:`), and a lot of the wave that has not started has no branch to read yet. An unreadable repository is the warning `précheck de partage : lecture impossible (…)`; the lot goes on.

## The edge-case probe (`orchestrate.probe`, L497)

Code bugs are the first cause of correction passes, and an edge case is the first sub-cause of those (64 % of the `bug-code` passes since the instruction of L447, 69 % before: writing it in the brief changed nothing). `orchestrate.probe: true` adds a step between the writing and the review: a **fresh Sonnet session** (`probe`, brief `templates/orchestrate/probe.md`, `effort.probe` medium, the delay of a write step `timeouts.work`) that has not written the code, reads the lot's diff, and tries to break it with tests at the edges: empty, absent, twice, wrong type, refused, the real shape of the data, the other callers. The diff is given as a command (`git diff <start sha>..HEAD`), never pasted; the sheet of the lot is named when there is one. Like `implement` and `fix`, the brief gives the program's exact gate (L399: the probe commits tests the gate replays, `tsc` and the quality script included) and the session's machine share (L350). The session writes its tests in new files and commits, with `probe(L<n>): …`, only those the project's gate plays and that are green at the lot's last commit, plus those that are red because the code breaks a rule of the lot; an expectation outside the rules of the lot is reported (`horsRegle`), not committed (see « What the probe commits » below); it does not touch the application code nor the sealed acceptance tests.

```yaml
orchestrate:
  probe: true   # true or false; absent = nothing changes (no session, no field in the journal, no line in the output)
```

**When it plays.** Once per lot, after a writing session whose gates are green (tests, build, acceptance) and after the « code sans test » gate, before the librarian and the review; never during the minors pass, never for a lot with no commit. It is recorded in the lot's state (`probe`): a resume does not replay it, except after a quota, where it is the step that was interrupted. `--dry-run` lists the `probe (sonnet)` step between `implement` and `review`.

**What a red test does.** After the session the program plays its own gate (`orchestrate.build`, `orchestrate.test`) as after any writing. A test red **now and not at the start sha** (never a failure already there, L213) sends the lot to a correction pass (`fix`) before the review, with a finding of severity *major* whose text starts with `sonde de cas limites : ` and names the test; the probe's own report (`echecs`, « test — edge — expected ») is added to it so the fix session sees the edge. Without `orchestrate.test` there is no gate to read: the failures the session announces are taken as they are, with the warning `sonde de cas limites : échecs annoncés par la session, non vérifié par le programme (orchestrate.test absent)`. All the probe's tests stay in the lot. A file committed by the probe that is neither in `orchestrate.testGate.tests` nor a test file at any depth (`*.test.*`, `*.spec.*`, `test/`, `tests/`, `__tests__/`) is a warning that names the files (`sonde de cas limites : la session a modifié du code hors tests (…)`); nothing is removed.

**An out-of-rule expectation of the edge-case probe never buys a pass (L625, issue #41).** What the probe reports in `horsRegle` is only a warning and a `[hors règle] …` proposal; it opens no correction pass. The code review that follows does not turn it into one either: its brief lists these expectations (at any rank, the probe plays before review 1) and asks not to report them at all (neither blocking, major nor minor: they are not findings of the lot), and a **major or minor** whose text contains an expectation word for word (`setAsideHorsRegle` in `src/orchestrate/cycle/converge.ts`) is not counted, with the warning `<majeur|mineur> qui reprend une attente hors règle de la sonde, non compté (déjà proposée au lead)`: a major so set aside buys no correction pass, a minor so set aside does not open the minors pass of a non-light lot and is not proposed as `[mineur code]` (the `[hors règle]` proposal already carries it). When this makes the review conforming, the agent's « non conforme » verdict (it counted the major) is replaced by a `conforme, … attente hors règle …` note (`horsRegleNote`), as `convergedVerdict` does for unchanged majors: `raf done` and the delivery audit would otherwise refuse the lot. A blocking finding always counts; a reworded major is not recognised (known limit, the brief is what asks the reviewer not to).

**What the probe commits (L580, issue #37).** A probe file is committed only if the project's gate plays it (the brief gives the gate's commands; the file goes where the test runner and `orchestrate.testGate` pick it up) and if it is green at the lot's last commit; otherwise it is not committed and the brief asks the session to delete it. A file the session leaves **untracked** anyway (written, played, never committed) is not a dirty repository: the program removes it and writes the warning `sonde de cas limites : fichiers non commités laissés par la session retirés (<files>)`, the same as after a cut probe, and the review goes ahead; a **tracked** file modified and left uncommitted still hands the lot back (`dépôt sale après probe : <files>`). **A file the probe staged (`git add`) and did not commit is removed too (L614, GitHub issue #39).** Since 1.53.0 a red probe file was often left *indexed* (`A  <file>`): it is not untracked, so it counted as a tracked modification and the lot came back `dépôt sale après probe`, its findings lost. The program now treats a **new file in the index** (status `A`, absent from HEAD, not there before the session) like an untracked one: it takes it out of the index one file at a time, deletes it, and names it in the same warning (`fichiers non commités laissés par la session retirés (<files>)`, decoded paths). A tracked file modified or staged still hands the lot back. **The red cases come back as findings**: when a file was removed and the report's `echecs` lists cases, each becomes a *major* finding of the correction pass, `sonde de cas limites : <case> (fichier non commité, retiré par le programme : <files>)`, **with `orchestrate.test` too** (the gate no longer sees the removed file, so it cannot report them); without `orchestrate.test` the announced failures were already findings and are not doubled. No `echecs`, no finding. The `horsRegle` entries are noted before those checks, so a handed-back lot keeps its warnings and proposed sub-tasks. A test that fails because the code breaks a rule of the lot (fiche or goal) is committed red and the correction pass turns it green. An expectation that is not a rule of the lot (a wrong type, a blank name, a value the API server already refuses) is not committed: the session lists it in the optional report field `horsRegle` (« test — edge — expected »), and the program writes one lot warning per non-blank entry, `sonde de cas limites : attente hors règle du lot, non commitée (sous-tâche proposée au lead, hors des constats de revue) : <entry>`, and one proposed sub-task `[hors règle] <entry>` (`proposals` of the lot, handed to the lead, without duplicate); it never sends the lot to correction. Since L625 the code review's brief lists these expectations and asks not to report them, and a major or minor that repeats one is not counted (rule above, « Out-of-rule expectations never buy a pass »). An absent, empty or mistyped field gives nothing. The brief also asks the file to respect the repository's linters (shellcheck for a shell script, eslint, the lint target or CI). The program does not run the linters itself: the lint belongs to the gate only if the project's `orchestrate.build` includes it.

**Cost and limits.** The probe's session counts in the lot's tokens and budget. The correction it triggers is one of the two ordinary passes (`MAX_PASSES`): after it, one pass is left for the review, so the librarian is not called (the `bibliothécaire non appelé` warning says so, and the review carries the documentation gap). The probe does not play when a correction pass is already done, or when the budget does not pay the probe (estimated at 65 k tokens, `PROBE_RESERVE`, no measure yet), the correction and the review that follows: the warning `sonde de cas limites non jouée : <n> passe(s) de correction déjà faite(s) ou budget du lot (<count>) insuffisant` says so and the review goes ahead. If the red tests cannot be corrected for lack of budget after the probe, the lot goes back to the lead without a review, with its findings, as for any red tests after a writing (L145). Without a new commit from the probe, the review keeps the results of the gate played after the writing (it does not rerun the suite and the build).

**It never blocks the lot.** A failed, cut or timed-out session, or an unreadable report, is the warning `sonde de cas limites non jouée : <cause>` and the review goes ahead; the questions of the report become warnings, nobody waits. A quota suspends the wave like any session and the resume replays the probe. What a cut session committed before the cut goes through the same checks as an answered one (commits in the journal, lock on sealed tests, warning for files outside the tests). What a failed or cut session leaves uncommitted, staged or not (a cut between `git add` and the commit is ordinary), is put back (index unstaged, tracked files restored, new files removed) with a warning that names the files, so a timed-out probe never hands the lot back for a dirty tree. Only a violation of the lock on sealed acceptance tests, or a dirty repository after a session that did answer, hands the lot back, as after any writing session.

**Measuring it.** The key is set in cadence's own `cadence.yaml` only, as a trial, and the lead sets it to `true` after the release is in service. Keep or drop it on figures: `cadence corrections <folder> --since <date>` (share of `bug-code` and of `cas limite` among the correction passes, lots with 2 passes or more, L430) and `cadence perf` (the `probe` step has its own row; tokens per lot). The `probe` step keeps the texts of the findings it sent to correction (`constats`, each starting with `sonde de cas limites : `): `cadence corrections` reads them as the findings of the `fix` pass that follows, in place of a review's. The pass is also told apart by the `probe` step that precedes the `fix` step and by the lot's warning `sonde de cas limites : <n> constat(s), passe de correction avant la revue`; the finding given to the fix session starts with `sonde de cas limites : `.

## A goal that narrows a lot to commits already merged (L621)

GitHub issue #40: a lot mostly merged and relaunched with `--goal "the four remaining fixes"` went through spec → mockup again and its reviews judged every commit of the lot, so a finding outside the goal bought a correction pass (74 min and 1.28 M for a commit of four fixes).

- **Narrowed lot.** A lot is *narrowed* when a goal is given (`--goal`, else the plan's `goal:` key) and at least one work commit of the lot is already in the base branch at launch. The commits are read with `lotWork`, in the project's repository only: a lot whose merged commits are only in a neighbouring repository (`repos:`) is never narrowed. Nothing else enters the definition (visibility, screen or spec step), so an invisible lot can be narrowed too.
- **Mockup skipped.** A narrowed lot whose goal does not change the layout starts without a spec step or mockup: no `screen` in its state, first session `implement`, the budget of the implementation alone, and the journal says `<project>:<lot> · maquette sautée : l'objectif rétrécit le lot à N commit(s) déjà intégré(s) et ne change pas la mise en page` (N counted before the first session; no state field: the journal line re-runs `launchScreen`, `src/orchestrate/cycle/retreci.ts`, at the lot's first start). The goal changes the layout when its text, without accents or capitals, contains one of: `mise en page`, `layout`, `disposition`, `maquette`, `ecran`, `affichage`, `colonne`, `grille`, `responsive` (a hypothesis of the sheet: a word to add or remove changes only whether the mockup is played). A lot with a sealed acceptation keeps its full chain, a `spec: true` lot without a screen keeps its spec session (a `spec: true` lot with a screen skips like the others, budget of the implementation alone), and without a goal or merged commit nothing changes.
- **Reviews judge the diff of the goal.** The brief of the code reviews (`review`, `review-small`) of a narrowed lot says, from review 1: judge only the commits after the launch head (`git log <sha>..HEAD`, `<sha>` = `headBefore` of the lot's first step) against the goal, the earlier commits being context; and mark `inchange: true` on every major outside the goal and outside the changed lines. From review 2 the L622 brief is kept (once) with the range line added.
- **The mark counts from review 1.** For a narrowed lot, a major marked `inchange: true` is set aside from review 1 (L622 reads the mark from review 2 only): `[suite code] <file>:<line> — <text>` in the proposals, `conforme, N majeur(s) sur un point inchangé en suite pour le lead : …` in the verdict, no pass. A blocking finding always buys a pass; a major inside the goal or the changed lines counts; a major marked that repeats the previous review still counts (false mark, from review 2 on). A lot that is not narrowed keeps L622 as it was.
- **Read from git, no state field for the verdict.** The reviews read the narrowing again each time (`readShrunk`): the state keeps a goal and at least one commit of `lotWork` is an ancestor of (or is) `steps[0].headBefore` and the range to judge starts at the lot's real base (`git merge-base <headBefore> <tree.base>`, equal to `headBefore` at a first launch). Commits written by the wave come after `headBefore`, and the unmerged commits of a branch taken back (L311) stay in the range to judge, not in the context, so a resume never narrows a lot after the fact nor un-narrows it. Without a goal, without `headBefore` or if git cannot answer, the lot is read as not narrowed (ordinary path). Known limit: a lot taken back by `--add` keeps the steps of an earlier wave, so `steps[0].headBefore` is that of the first wave.
- **Edges (L634).** The express lane reads the `screen:` of the *plan*, not the state's: a `screen: page` lot of 0.1 day or less whose mockup was skipped is not express. Only `page` counts: a `component` or `journey` lot of 0.1 day or less stays express, as before. The integration re-review (`git diff <base>...HEAD`, `integrationText`) does not receive the `<sha>..HEAD` range, which would contradict it. For a lot with neighbouring repositories the brief adds that the range is the project repository only and that every commit citing the lot is under review there. `--dry-run` computes the budget basis from the lot as launched (no spec stage for a skipped mockup), like the budget it announces.

## The review loop: classes, tests that guard nothing, minors already noted (L646)

Three rules cut the correction passes that a fresh review reopens with the same defect.

- **The fix brief gives the findings by class and requires the class.** The review schema gives each finding an optional `classe` (`bug-code`, `architecture`, `test`, `code-mort`, `erreur-avalee`, `documentation`, `convention`: the grid of the code-reviewer; any other value is dropped). `{{constats}}` of the fix brief groups the findings of the previous review under `Class « … » (n findings)` (a finding with no class goes under `other`; with no class at all the list stays flat) and adds that every other instance of the class must be fixed in the diff of the lot and in the callers, each with its own test (`src/orchestrate/constat-classes.ts`). Only the `fix` template gets this: the librarian pass (`fix-docs`) and the minors pass (`fix-minors`) get the flat list, their own rule (« documentation and nothing else », « fix each minor that is right ») would contradict it.
- **A test added by the lot that stays green without the lot's changes is sent back to correction** (`src/test-sans-code.ts`, `src/orchestrate/cycle/test-vert.ts`). At most once per lot, after a writing whose gates are green and after the « code sans test » gate, before the probe, the program replays alone each test file the lot **added** (in the diff from the lot's start sha to `HEAD`, the lot's repository only, not its neighbours: a moved test counts as added, a modified test does not; `orchestrate.testReplay`, `{files}` replaced; at most 10, a warning names the rest) in a throwaway worktree at `HEAD` where every file of that diff that is not a test (`orchestrate.testGate.tests`) is back to its state at the start of the lot, or removed if the lot added it: code, but also templates, docs, `package.json`. Test files stay as they are at `HEAD`, and `orchestrate.testGate.code` minus `except` only decides whether the gate plays at all. The worktree holds tracked files only: the folders of `orchestrate.worktreeDeps` present in the lot's tree are linked into it (symlinks, not copies), and without the key only the root `node_modules` is. A project whose tests need `frontend/node_modules` or `.venv` must declare the key for this gate, even when `cadence verify --gate` finds them without it: otherwise the replay fails at load and the gate refuses nothing, with no warning. Exit code 0 there means the test guards nothing the lot changed: a major finding (class `test`) goes to a direct fix, like « code sans test ». Any other exit code is not a green (127 for a command not found, a failure at load, the 5-minute timeout of a replay): that test is not refused, and no warning says so. The gate needs `orchestrate.testGate`, `orchestrate.testReplay`, an `orchestrate.test` that is not a list of parts, and a start sha; it is not played in express mode or in the minors pass, and it replays nothing with no added test or no changed code file. When a correction pass is already used or the budget does not pay the correction (the same conditions as « code sans test »), the replays still run but nothing goes to correction: a warning names the tests. It counts as a program pass: a light lot's review stays the light one for it, and a lot handed back at the wall cap by this gate can be resumed by `--add`.
- **The next review does not re-read a minor already noted.** The brief of a code review of rank 2 or more lists the minors of the previous review apart (« already noted, do not report them again »), not among the findings the author had to fix; a minor of the report with the same file and text as one of them, or (L649) the same file and the same line, or the same file and the same `classe`, however it is worded, does not count (decision `ecarte-deja-note` in `constatsRevue`, a warning on the lot), so it does not reopen the minors pass. A major or a blocking finding with the same text counts. Only the full review sets it aside, and only the full review lists it apart: the short review that follows the minors pass (`review-small`) gets the minor under « had to fix » and keeps counting it, so a minor the pass did not fix still goes to the lead. A minor stays noted from one full review to the next even when the review does not count it again (the brief told the reviewer to be silent, or it was set aside): a third full review still sees it in its brief and does not count it. A reworded minor on another line, with no class in common, is not recognised. The same comparison reads the false `inchange` mark of L622.
