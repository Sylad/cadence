# Goulot « bug de code » : ce qu'il y a dedans, ce qui change, comment le mesurer (L428)

`cadence perf` du 2026-10-29 (fenêtre 23–29-10) pose le goulot : **100 passes de correction sur 143 classées sont un bug de code** (70 %), devant la dérive d'architecture (18) et la spec floue (13) ; 31 % des passes restent à classer et 37 passes sans revue (tests rouges) sont comptées à part. Décision de Sylvain du 29-10 : lire ces passes, retenir les causes dominantes, changer le maillon qui les produit, mesurer sur deux fenêtres.

## 1. Classement par cause

Commande : `cadence corrections --since 2026-10-22` depuis le dossier des projets (journaux de vague de tous les projets, classement mis en cache par `--classify`, modèle local Ollama).

| Cause | Passes | Part |
|---|---|---|
| bug de code | 122 | 44 % |
| dérive d'architecture | 23 | 8 % |
| spec floue ou critère absent | 15 | 5 % |
| test manquant | 11 | 4 % |
| règle de gestion inventée | 4 | 1 % |
| sans revue (tests rouges) | 38 | 14 % |
| non classé | 64 | 23 % |

277 passes sur 362 lots, tous projets (cadence : 69 bug de code sur 143 passes). `bug-code` est la seule cause qui domine ; les six autres, ensemble, pèsent moins. Le classement en sept causes ne dit pas **quel** bug : la section 2 le lit.

## 2. Lecture des passes « bug de code »

Lecture à la main de la première constatation de 75 des 122 passes (`cadence corrections --since 2026-10-22 --sample 400`, passes classées `bug-code`), pas un comptage automatique : les chiffres de famille ne sont donc pas donnés, seulement ce qui revient. Trois familles couvrent presque toutes les passes lues :

1. **Un cas limite que le code ne tient pas, ou que rien ne teste.** Entrée vide, absente, en double, d'un autre type, refusée, ou forme réelle des données différente de la fixture. Exemples : `raf` plan hérité, `git mv` qui échoue quand `.cadence/` n'existe pas (L246) ; nom accentué relu en latin1 par multer (finance-tracker L110) ; élément dont `type` n'est pas une chaîne (L263) ; étiquette longue qui fait planter `lead hold` avec une pile Node (L255) ; pluriel et plage de « Figures 2–4 and … » (L261, L274) ; valeur entre guillemets non fermés non masquée (L294) ; numéro 99 pris pour « inconnu » (ol-companion).
2. **Une affirmation fausse écrite dans la documentation, un commentaire ou un rapport.** Un chiffre mesuré sans l'être, « aucun », « toujours », une doc qui décrit l'ancien comportement. Exemples : README qui cite une durée de 40 s fausse (warhammer40k L166) ; rapport « les cinq étapes ux sont sous le seuil » alors que le seuil est 5 (L280) ; documentation du bibliothécaire ou de `--follow` qui décrit autre chose que le code (L329).
3. **Un test qui ne peut pas échouer, ou un comportement ajouté sans test.** Titre qui annonce plus que l'assertion (maritime-atlas Q-DON1, Q-SST1), branche nouvelle jamais jouée (L252, L311), test qui n'exerce qu'une classe CSS sous jsdom (finance-tracker L144).

La famille 1 est la plus fréquente. Les trois ont la même origine côté brief : la session `implement` relit son diff « au hasard » (la grille de l'auto-vérification L236 nomme les cas limites sans demander de les énumérer ni de les tester) et ne rattache pas chaque règle à un test et à une ligne.

## 3. Le maillon changé

Le brief `implement` (`templates/orchestrate/implement.md`) porte, entre la liste d'auto-contrôle (L222) et le parcours réel (L344), un bloc « Limits and rules, before the walkthrough » :

- par règle (`Rn`) : le test qui échoue si le code la casse **et** la ligne qui la tient ; sans le couple, la règle n'est pas faite ;
- par fonction, motif, seuil ou commande ajouté ou changé : énumérer les entrées aux bornes (vide, absent, deux fois, mauvais ordre, mauvais type, refusé, forme réelle des données, autres appelants) et donner à chacune un test qui échoue sans le code ; un cas listé non testé va sous `nonVerifie` ;
- par chiffre, « tout », « jamais », « toujours » écrit en README, docs, commentaire ou test : le vérifier contre le code ou en l'exécutant.

Le brief `fix` ne change pas (ses passes corrigent des constats précis) ; la revue non plus.

## 4. Mesurer l'effet sur deux fenêtres

Le brief d'une vague est celui de l'instantané pris à sa création (`<vague>/tool/`) : seules comptent les vagues **créées après** la mise en service de ce lot. Pas de mesure possible avant : cette page donne le point de départ et le protocole, les lignes « après » restent à remplir.

Pour chaque fenêtre de 7 jours qui suit la mise en service (F1 puis F2) :

```sh
cadence perf                                   # ligne « causes dominantes (N passes classées) : 1. bug de code … »
cadence corrections --classify --since <début de F>  --until <fin de F>
```

| Fenêtre | Passes classées | bug de code | Part | Lots à ≥ 2 passes |
|---|---|---|---|---|
| Avant : 23–29-10 | 143 | 100 | 70 % | 25 % |
| F1 (après) | à mesurer | à mesurer | à mesurer | à mesurer |
| F2 (après) | à mesurer | à mesurer | à mesurer | à mesurer |

Lecture : le brief est utile si la **part de bug de code baisse** sur F1 et F2 sans que les lots à au moins deux passes montent (une part qui baisse parce que les autres causes grossissent n'est pas un gain). Les passes « sans revue » et « non classé » changent le dénominateur : classer d'abord (`--classify`), comparer ensuite. Si F1 et F2 ne baissent pas, relire les passes de la famille qui reste (section 2) : le maillon à changer est alors la revue ou la fiche, pas le brief.
