# cadence-hud

A band above the Claude Code prompt (terminal and desktop app), refreshed every 5 s:

```
ctx ▰▰▰▰▱▱▱▱▱▱  42 % 84k/200k  │  5h  23 % ↻ 2 h 10  │  7j  61 % ↻ 6 j 15 h  │  $1.23  │  fable 410k sonnet 85k  │  ⚙ 2 agents  │  2 cmd
⟳ cadence · 2026-10-07-2131 en cours  │  budget ▱▱▱▱▱▱▱▱▱▱   1 % 14k/2M  │  1 session/2
  L112  implémente  implement@sonnet 34 s         global-setup coupe le cache de compilation de Node...
```

Context of the session (green / orange / red at 50 and 75 %), the 5-hour and 7-day quota
windows with the time to their reset, the cost of the session and its split per model, the
subagents of this session, the background commands in progress (`2 cmd`: Bash run in the background and Monitor, subagents' included, as the app's "background commands" card counts them), and every live `cadence orchestrate` wave: budget, sessions, one
aligned line per active lot (status, step, model, elapsed, start of the title; `porte@tests 3 min` while the program's build or test gate runs with no session, L395), the lots still
waiting. When no wave is running, the last finished one stays on a grey line for 30 minutes
after it ended, then disappears. A background command counted for more than an hour, or with no
record of when it started, is no longer shown as running: it moves to a grey `N cmd sans fin
vue` ("end never seen") right after `N cmd`, because its end notification may never have reached
the session. Waves are read from disk (`~/.cadence/orchestrate/waves/`, then `.cadence/runs/`); no
cadence command is run, and the CLI is not required for those. One more block needs it: the **progress of the plans**,
one line per active project (a project with open lots), in the order of `priority:`:

```
ol      ▮▮▮▮▮▯▯▯▯▯ 39/78 · 0 en cours · +3 cette semaine
cadence ▮▮▮▮▮▯▯▯▯▯ 10/20 · 2 en cours : L149 L153
```

The **sessions of the lead** (L276) — the ones started by hand and declared with `cadence lead hold <label>` — are drawn
under the waves, even when no wave is running: the slots line of `cadence orchestrate --status` and one line per session
(label, age, time left):

```
sessions du lead : 1 · créneaux libres : 2 sur 3
  correctif-L12  depuis 4 min · reste 56 min
```

With a live wave and no held session the line reads `créneaux libres : 1 sur 2`; with neither, nothing. A session whose
time limit has run out stops counting in the slots but is not dropped (L278): a row `⚠ session du lead échue : correctif-B28  échue depuis 2 h 10` stays under the others (in red) until `cadence lead release <label>` or a renewed `lead hold`, since nothing stops the session itself. They are read from disk (`holds/` of the cadence home), like the waves.

The bar is lots done over lots done + in progress + to do (dropped and recurring lots left out); the count of lots in progress is followed by their ids (`2 en cours : L149 L153`), cut to three then `…` (`5 en cours : L1 L2 L3 …`), the count alone at zero;
`+N cette semaine` counts the lots created in the last 7 days (today and the six before) and is left out at zero. The source is
`cadence lead tour <folder> --json` (the folder a wave was launched from, otherwise the session's: a folder of projects gives one line per project, a project with no sub-project gives its own single line),
read again at every wave transition and otherwise every minute; without `cadence` on the PATH, the
lines are simply not drawn.

Install it as a plugin from the same marketplace:

```
/plugin marketplace add Sylad/cadence
/plugin install cadence-hud@cadence
```

`/hud` hides or shows the band. `/hud cmd` lists the background commands being counted (id, tool,
origin `session` or `agent <id>`, age, name; `(sans fin vue)` on the ones above). Any other argument
`/hud projets` folds the project list to one line, and opens it again. Any other argument
answers `argument inconnu : … (attendu : cmd, projets, lots)` and leaves the band as it is.

### The lots panel (`/hud lots`, L401)

`/hud lots` opens a **panel**, beside the conversation (inline above the prompt on the main screen); the same command closes it. It is never opened on its own, and the command opens it whatever the width of the window, Claude placing it; when Claude cannot place it, the command answers `panneau des lots non placé : <reason>` and nothing opens. For each project of the folder (the order of `priority:`) it draws the open lots as a tree, with their state and their `after:` links:

```
Lots  glisser un lot, ou Alt+↑ / Alt+↓  lu à 15:52
▾ cadence  7 lots non clos
 ▾L401        Panneau des lots (mod cadence-hud, Pane)  2 sous-lots  ▶ en cours
  ├ L401/2    Écrire le panneau et son rafraîchissement      ▶ en cours
  └ L401/3    Test du rendu (claude plugin test) et doc      ○ à faire
  L402        Réordonner par glisser-déposer  after: L400 L401   ⊘ bloqué
▾ ol  1 lot non clos
  L80         Calendrier des matchs                          ⟳ relit
/hud lots pour fermer
```

Each project name is a button (L409): a click, or Enter once it has the focus (click in the panel, or ctrl+x then tab), folds the project to one line (`▸ maritime  159 lots non clos · 3 en cours`, the name, the open lots and those in progress) or opens it again (`▾`). `/hud lots <project>` does the same from the keyboard (`projet inconnu : … (projets : …)` for a name that is not in the panel). A project with more than 20 open lots (native sub-tasks not counted) is folded until you choose; your choice wins over that default either way, and it is kept between two openings of the panel and between sessions (the plugin's `$.store`, key `lotsFolds`). A folded project that is shown is not counted in `… +N lots de plus`, and when the panel is short it keeps its line even after the cut (the open lots before it give way); if there are more folded projects than the panel has room for, the ones left out are counted there with their open lots. A project the tour could not read has no button.

Inside a project the lots are ordered (L410): those in progress first (`doing`, or in a wave being implemented, reviewed, corrected, in question, ready or handed back), then the free ones (no open `after:`, whatever the wave state of a queued, failed or suspended lot), then the rest (blocked by an open `after:`), the order of the plan kept within each group. A sub-lot stays under its parent, and a parent with a sub-lot in progress rises with it (that sub-lot before its siblings).

A project shows at most 5 lots (L411), the first ones in the order above (so those in progress first); a lot and its sub-lots count for one, and the project's count (`12 lots non clos`) stays whole. Past 5, a `+ N lots` button (`N`: the lots left out) opens the rest of the project, and turns into `moins`, which closes it again. A lot that has sub-lots (a sub-lot of a plan, or native sub-tasks) shows `▸` (closed) or `▾` (open) glued to its id, in the last cell of its indent and their count after its title (`2 sous-lots`); it is closed by default and a click opens or closes it, at any depth (where the panel is drawn by a `Client` region — terminal and desktop, see Reordering below — the click is on its `▸`/`▾` cell, or Enter on the selected row: the id itself selects the row for a drag). Both choices are kept between two openings of the panel and between sessions (the plugin's `$.store`, key `lotsViews`); a folded project (L409) shows neither lots nor button. `… +N lots de plus`, when the panel is short, counts lots only, never these buttons; when the panel is short, the button of the project being cut keeps its line (like a folded project) and the lots give way, so `moins` is always there to close the rest, and the lots hidden behind a button that is cut with its project are counted in `… +N`.

**Reordering (L402).** Drag a lot onto another lot of the same project and of the same display group (or a sub-task onto another sub-task of its lot, same group): press on the row, move with the button held, release. While you drag, the row you started from shows `●` and the row under the pointer shows where it will land, `⇡` (before it) or `⇣` (after it), or a red `⊘` when it belongs to another parent or to another display group (L410) and the drop will be refused. The keyboard does the same wherever the panel is drawn by a `Client` region (terminal and desktop app): click a row (or press ↑ / ↓ once the panel has the focus), then **Alt**+↑ / **Alt**+↓ moves the selected lot before its previous sibling / after its next one. Only the rows the panel shows take part (L411): a lot hidden behind `+ N lots`, or the sub-lots of a closed lot, are not rows, so they are never a target — Alt+↓ on the fifth lot, the last row before the `+ N lots` button, moves nothing, like Alt+↓ on the last row of a project; open the rest (or the lot) first, and the drop runs `raf move` as usual. The `+ N lots` / `moins` button sits outside the `Client` region, after the project's rows. The drop runs `raf move <id> --before|--after <id>` ([raf move](raf.md)) in the project folder, then the panel reads the plans again and says, under the title, `✔ L13 placé avant L10 — le plan est modifié, à commiter (raf move ne commite pas)`: the panel never commits, the plan file is yours to commit. Everything is relative to what the panel shows, in the L410 order, not to the order of the plan: the row you drop on, and the "previous" and "next" sibling of Alt+↑ / Alt+↓, are the ones displayed around the lot, and `raf move` is given that lot as its target. **A lot is reordered only inside its display group** (L410: in progress, free, blocked): dropping a lot on a lot of another group is refused, `raf` is not called and nothing moves. While you drag, the row under the pointer shows the red `⊘` (as for another parent), and on release the panel says why, by group: `✖ L411 est en cours : un lot libre se range parmi les libres` (the words: `en cours` / `libre` / `bloqué`; the lot is named by what it is, `un lot` or `une sous-tâche`). A parent with an in-progress sub-lot is shown with the lots in progress, so it counts as one of them. Alt+↑ / Alt+↓ toward a displayed neighbour of another group gets the same refusal; at the edge of the displayed rows (or before the `+ N lots` button) nothing happens. (Case that led to this: plan L402 L403 L407 L411, L403 free dropped on L411 in progress moved L403 below L407 and hid it behind `+ 11 lots`.) Inside a group the screen follows the plan, so a gesture that goes through always shows: the lot moves where you dropped it. A drop that would leave the order of the group as it is — the lot is already right before (or after) the target among the lots of its group — runs nothing and says `• L10 est déjà avant L13 dans le plan : rien à déplacer`; no gesture of the panel leads there (the screen follows the plan inside a group), the check guards a request the drawing did not make. The same holds between the sub-tasks of a lot. The `déjà` check is made on the table the panel last read: from a successful `raf move` until the end of a re-reading started *after* it (`cadence lead tour` takes several seconds; a reading already in flight read the old plan, so another one follows it) the table is held stale: no `déjà` short-circuit, `raf move` runs and decides (the group refusal stays: it depends on the states, not on the order). A refusal is written under the title with its reason and nothing moves: a wave holds the repository (`move : orchestration en cours …`), a plan kept by another tool (`plan en lecture seule : … — le modifier avec l'outil du projet`, the message does not name that tool's command: `raf` does not know it, so look in the project), an archived lot, different parents (`L402 et L401/2 n'ont pas le même parent …`) or different display groups (`L411 est en cours : …`), the last two checked before `raf` runs; `raf` missing from the `PATH` says so. On a surface with no `Client` region (mobile, editor) the panel stays read-only (`lecture seule` in its title).

**Reordering the projects (L449).** Above the tree, `ordre des projets (priority:) — glisser, ou Alt+↑ / Alt+↓` and one row per project (`cadence  7 lots non clos`; `illisible` for a project the tour could not read), in the order of `priority:`. It is drawn only where the lots can be reordered (a `Client` region: terminal and desktop app), when the folder has two projects or more, and when the panel is tall enough to keep a row for each project and one lot under it (otherwise the tree has the room). Drag a project onto another (`●` the row you hold, `⇡` / `⇣` where it will land) or click it and press **Alt**+↑ / **Alt**+↓ (↑ / ↓ alone select): the drop runs `cadence lead priority <project> --before|--after <project> <folder>` ([lead priority](lead.md#lead-priority)), which rewrites the `priority:` list of the `cadence.yaml` of the parent folder, comments kept; the panel then reads the plans again and says under the title `✔ ol placé avant cadence — priority: du cadence.yaml est modifiée, à commiter`. This order is the one of the tour, of `cadence orchestrate --continue` and of the panel itself. The panel never commits. A refusal is written under the title with its reason (`✖ /dev/cadence.yaml illisible : …`, a `priority:` that is not a list) and nothing is written; `cadence` missing from the `PATH` says so; a project already at that place says `• … est déjà avant …`. The error row `cadence.yaml` that the tour adds for an unreadable file is not a project and cannot be moved or targeted.

States: `▶ en cours` (doing), `○ libre` (todo, no open `after:`), `⊘ bloqué` (todo, an `after:` is still open); a lot in a wave takes the wave's state and words, as the band writes them (`… en attente`, `⟳ implémente`, `⟳ relit`, `⟳ corrige`, `? QUESTION`, `✔ prêt`, `↩ rendu`, `✖ échec`, `⏸ suspendu`). In a native plan the sub-tasks of an open lot (`L401/2`) are its sub-lots (`├`/`└`); they only read `▶ en cours` or `○ à faire`, and are not counted in the project's `N lots non clos`. In a plan kept by another tool the sub-lots come from `parent:`. An `after:` id that is closed or unknown is struck through and blocks nothing. A project the tour could not read shows `illisible : <error>`; the others stay.

Before the first reading the panel says `Lecture des plans…`; if `cadence lead tour` does not answer it says `Lots illisibles : cadence lead tour n'a pas répondu. Nouvelle lecture dans une minute.` (a failed re-reading keeps the last table); a `cadence` too old to give the `lots` field says `Lots indisponibles : cadence est trop ancien, mettez-le à jour.`; with no open lot, `Aucun lot non clos dans les projets de ce dossier.`. A tree taller than the panel ends with `… +N lots de plus`. Under 60 columns the `after:` list moves to its own line and the title is cut with `…`, never the id or the state.

**The cycle of a lot as a strip (L413).** Under a lot, one line draws where it stands in its cycle, read from the wave state (`.cadence/runs/<wave>/<project>--<lot>.json`, whose steps the collector returns as `trail`: kind, status, start, end) and from the plan (`reviewed: true` in the lot's tour row when the plan holds its code review). The wave's stages, in order: `fiche` (the `spec` and `fiche` sessions), `maquette`, `accept` — these three only when the lot played them — then `implement`, `revue` (`review`, `review-small`), `correction` (`fix`), `porte` (the program's build or tests gate, which has no session), `UX`, `intégration`, `prêt`; the control `precheck` is not a stage. Each shows a glyph (`✔` done, `▶` current in bold, `○` to come, `✖` failed), its name, its passes — `correction n/3` (the lot's `pass`), `revue ×2` when the review ran more than once, the gate's `build` / `tests` — and its duration (the sum of its sessions, up to now for the one running; none when its dates are unreadable or the stage was not played). The current stage is the running session; else the gate while it runs; else, between two sessions, the lot's `next`; a lot `failed` or `handed-back` shows in `✖` the stage of its `next` (a lot handed back at integration: `intégration`), else its last stage played, a lot in `question` keeps it current. A stage never played that a later one has passed counts done (`porte`, a `correction 0/3`). Then the plan's: `revue posée → clos → livré` — the review is done when the plan holds it; the first undone one is current once the wave is `ready`. A lot with no wave gets the plan's strip only when it is `doing` **and** its review is posed (before, nothing happened that a strip could show); a `todo` lot, a sub-task and a lot of another project's wave get none. The strip takes one more row (it counts in the panel's height, in the `… +N lots de plus` cut and in the pointer region's rows) and is as wide as the body minus the id's indent; too long, it folds the finished stages into `✔ n`, then replaces the arrows with spaces, then cuts its end with `…`. Computed by `hooks/cycle.ts` (`cycleOf`, `cycleSegments`), drawn by `hooks/lot-row.tsx`; tested by `tests/cycle.test.ts` (L413 R1 to R15), `tests/lots-pane.test.ts` (R16, R17), `test/hud-cycle.test.ts` (R13: the real collector) and `test/lead-tour-lots.test.ts` (R12: `reviewed`).

**Lots in progress: budget and duration (L414).** Under the decisions block, `Lots en cours : budget et durée (N)` shows, for each lot being worked in a **live** wave (`implementing`, `reviewing`, `fixing`, `question`), one line `▶ project:lot  100k/750k tokens · 10 min (habituel 30 min)`: the tokens counted by the lot's steps over its budget, the time elapsed since its first step started, up to now — a program gate (build, tests) runs with no session while the lot stays in progress, and the usual time counts those gates too —, and the usual time of a lot of the same size. A lot that goes over comes first, in the warning colour, prefixed `⚠`: `⚠ cadence:L64  786k/750k tokens dépassé · 53 min (habituel 30 min, dépassé)`. **Budget over**: tokens above the lot's `budget` minus the share reserved for model escalation (`escalationReserve`) while the escalation is not engaged (ordinary passes do not spend it; once engaged it is released and counts); a lot state without `budget` shows the tokens alone and is never over. **Time over**: elapsed time above 1.5 times the usual time. The usual time is `lotMinutes` of `cadence perf --json` (`docs/perf.md`): the median wall time of the rendered lots of the same size class (the estimate, `0.5+spec` for a lot that went through the spec chain: the keys of `tokens.byEstimate`), the current window, else the previous one, the first with at least 5 rendered lots (`MIN_SAMPLE`, the same bound under which `cadence perf` refuses a trend): a window with fewer lots, even non-empty, gives no usual time. The mod reads it (`cadence perf <folder> --json`) with each re-read of the board **while a wave is live** (none without one, and no block), and keeps the last successful read when `cadence perf` fails or is missing. With no usual time for the lot's class (or no estimate in its state) the line shows the duration alone and never flags the time. The block is capped at a quarter of the body, decisions and lots in progress together at half of it (the tree keeps the rest); past that, the lots over first, then `… +N lots en cours`. **A lot that is over never loses its signal**: as soon as one lot is over, the block keeps at least two lines, the title and the first lot over, taken from the tree, even in a body of 7 lines or less or when the decisions fill their half (the finished waves of the last 7 days can). With no lot over, a block that has no room for two lines is not drawn and the tree keeps the body. Details in the plugin's README.

**Last delivery of each project (L415).** Under the lots in progress, `Dernière livraison par projet (N)` shows one line per project that has delivered: `✔ finance  3f9a1c2 · il y a 2 j · verte · 2 lots clos non livrés : L12, L13`, or `✖ … · rouge` in red when the last delivery failed; `rien à livrer` when every closed lot was delivered, and nothing after `verte` when the plan is not known. It reads the journal `cadence deliver` writes (`.git/cadence/deliveries.log`, one `day sha` line per green delivery, and `deliveries-failed.log`) through the `LAST_DELIVERIES` script (python3, the folder and each direct sub-folder whose `.git` is a folder, like the failed-delivery script; run at each 5 s refresh **while the panel is open**): the last delivery is the red one when `deliveries-failed.log` was modified after `deliveries.log` (the files' modification date decides, as for the failed deliveries), the green one otherwise; a repository with no readable line is absent. The age counts days from the journal's day (the journal has no hour): `aujourd’hui`, `hier`, `il y a N j`. **Closed lots not delivered**: `cadence lead tour --json` gives each project row `closed`, the closed lots (`done`, archived ones included, lots with an `every:` left out) as `{ id, finished }`; a lot is delivered when a green delivery happened on the day it was closed or after (the rule of the delivery delay in `cadence perf`), so it is not delivered when closed **after the day of the last green delivery** — a red delivery delivers nothing, and a project that never delivered green counts all its closed lots. A project absent from the tour, in error, or read by a `cadence` too old to give `closed` shows no count (not « rien à livrer »: we do not know). Order: red first, then the most undelivered lots, then the name. Height (`deliveriesHeight`): the title and one line per project, within what the decisions and the lots in progress leave of the half of the body, `… +N projets` when they do not all fit, nothing under two lines; the tree keeps the rest. Calculation: `hooks/deliveries.ts` (`deliveriesOf`, `buildDeliveries`, `parseLastDeliveries`). Tested by `tests/deliveries.test.ts` (L415 R4 to R11), `tests/lots-pane.test.ts` (R12 to R14, panel mounted), `test/hud-livraisons-l415.test.ts` (R2, R3: the real script on real journals) and `test/lead-tour-lots.test.ts` (R1: the `closed` field).

**What is waiting for a decision (L412).** Above the tree, a block `Ce qui attend une décision (N)` gathers what the person has to settle; it exists only when there is something to settle. It reads the band's waves (live ones, and the last finished one only when none is live), the finished waves of the folder that the collector returns apart in `ended` (whether a wave is live or not, without the band's 30-minute delay: **all** the finished waves of the last 7 days, with no cap on their number (a cost guard of 500 waves, far above the 162 waves per 7 days measured, is not a rule), newest first by the date of their `wave.json` — a question or a handed-back lot waits as long as the plan keeps the lot open and its wave is less than 7 days old (beyond that, the decision leaves the block even if the lot is still open in the plan), a newer wave finishing without that lot does not erase it; a live wave is not among them: its `wave.json`, always the most recent of the folder since orchestrate rewrites `consumed` in it, is skipped by the collector; the band and the tree keep reading `waves` only, their drawing does not change) and the failed deliveries; a lot counts once, in the first wave carrying it, live waves first then the finished ones newest first (taken over in a newer wave, that wave decides). Four kinds: `? project:lot  <questions>` (a lot in the `question` state; the short text is the first line of each question, joined by ` / `) with, below it in grey, the command that answers it (`cd <launch folder of the wave> && cadence orchestrate --resume --wave <wave> --answer project:lot "…"`, the one the end-of-wave table prints, preceded by a `cd` to the wave's `cwd`: orchestrate finds the wave only from there) — the same command while the wave is live (L407: orchestrate then drops the answer in the wave's queue, which the live wave reads between two steps, instead of refusing « la vague tourne encore »); `↩ project:lot  <cause>` (a `handed-back` or `failed` lot: the first line of its outcome, the status in words when empty; a `suspended` lot waits for nothing from the person), in red; `◐ project:lot  verdict UX : <verdict>` (a `ready`, visible lot whose review returned a verdict) with `cd <repository of the lot> && raf ux <lot> "verdict"` below (the `repo` of the lot state: from the parent folder raf answers « pas de plan », from another project it would record the verdict on that project's lot of the same id) — the commands to copy start with `cd` and run as they are from any folder, a path with a space or a quote is quoted for sh; `✖ project  livraison : <short sha> · <reason> (<day>)` in red (7 characters: deliver writes the full 40-character sha in the log). The block never takes more than half of the body (3 lines at least): past that, the first decisions that fit, then `… +N décisions de plus`. Failed deliveries come from the `DELIVERIES` script (collect.ts, python3), run at every 5 s refresh **while the panel is open**: for the folder and each direct sub-folder whose `.git` is a directory, the last line of `.git/cadence/deliveries-failed.log`, unless `deliveries.log` was modified after it (a green delivery clears the failure; file modification times decide, the day on the line cannot order two writes of the same day). The plan decides: the panel's board (read from `cadence lead tour --json`) drops any decision whose lot is no longer open in a project the tour read, so a UX verdict recorded then `raf done`, or a handed-back lot taken over and closed, disappears at the next plan read; a project missing from the board, in error or without lots keeps its decisions. The command to copy is wrapped over several lines at the panel's width, never cut, every line but the last ending with the shell continuation ` \` (`\` glued to the piece when a word longer than the line is cut): pasted as they are into a shell, the lines run one command, the whole one (without it, a first line `cadence orchestrate --resume --wave <wave>` ran alone, without its `--answer`); the wrapped lines count in the block's ceiling. Details in the plugin's README.

The data is the `lots` field of `cadence lead tour --json` ([lead tour](lead.md#lead-tour)), read together with the band's `progress` (same call, same folder). While the panel is open, the modification date of each plan (`.cadence/raf.yaml` and `cadence.yaml` of the folder and of its direct sub-folders) is read every 5 s, one `stat` each: a changed plan, like a wave transition, triggers a new reading before the minute is over. Cost of the `lots` field (R18, measured on 2026-10-28 with `cadence lead tour --json` on the parent folder of ten projects, three passes each): before L401 (cadence 1.19.1, no `lots`) 8.0 / 9.1 / 7.3 s and 86 KB of output; after (the L401 code) 7.5 / 7.0 / 8.4 s and 188 KB (192,503 bytes). The output more than doubles in size but the duration stays in the same order, under the 20 s refresh delay of the band, so the rule holds.

The source lives in [`plugins/cadence-hud`](../plugins/cadence-hud/README.md)
(its own README has the details of every cell); it is not part of the npm package. To work on it:
`claude plugin validate plugins/cadence-hud`, `claude plugin test plugins/cadence-hud`, and
`tsc -p plugins/cadence-hud` once Claude Code has loaded the plugin at least once (it generates
the `.claude-plugin/types` the tsconfig extends).

To load the mod from a local copy instead of the marketplace, put it in `CLAUDE_CODE_PLUGIN_DIRS` (for example `~/.claude/mods/cadence-hud`). On the cadence repository, `npm run service -- <sha>` keeps that copy up to date (L419): it synchronises `plugins/cadence-hud` of the version put in service into `~/.claude/mods/cadence-hud` (`--mod-dir` for another folder), leaving `.claude-plugin/types` alone. The folder must already exist; it is never created.

`node scripts/porte-mod.mjs` plays the two together (`claude plugin test`, then `tsc -p … --noEmit`, both even if the first is red). In cadence's own gate it is played by `test/porte-mod.test.ts`, since `vitest` excludes `plugins/**`: `orchestrate.test` stays the single `npx vitest run` (a composed gate would refuse `testReplay`), and a mod whose tests or typing are red turns the wave's gate red (L417).
