# Goulot « bug de code » : deux causes, une auto-vérification avant rendu (L543)

Suite de [L428](bug-code-2026-10-29.md) et de [L447](bug-code-2026-10-30.md). Le 03-11, `cadence perf` donne une part conforme du premier coup de **45 %** (précédente 63 %) et 141 passes de bug de code sur 214 classées. La consigne « edge cases » (L447) n'a pas déplacé la mesure : la mesure intermédiaire du 31-10 (`.cadence/raf.yaml`, lot L430 : cas limite 64 % des passes de bug de code, bug de code 51 % des classées, avant 69 % et 53 %) l'avait déjà vu. L543 classe la fenêtre courante avec la commande existante, retient les **deux** sous-causes qui pèsent le plus, et durcit une seule liste : « Self-check before handing back » du brief `implement`.

## 1. Tableau mesuré

Commande, jouée depuis le dossier des projets, telle quelle (aucune option nouvelle), sur des copies des deux caches pour ne pas toucher ceux du lead :

```sh
cadence corrections --classify --since 2026-10-27 --cache <copie de corrections.json> --cache-sous-causes <copie de corrections-sous-causes.json>
```

Ollama a répondu (modèle local `mistral-small3.2:24b`) : fenêtre du 27-10 au 03-11, 370 lots, 396 passes de correction dont 68 « sans revue (tests rouges) » que le modèle ne classe jamais, soit 328 passes classées, et **208 de cause bug de code** (63 % des classées, 53 % de toutes les passes). Les 208 passes sont sous-classées : 208 passes sous-classées sur 208. Aucune passe n'est classée à la main : chaque ligne vient de la commande.

| Sous-cause | Passes | Part | Maillon |
|---|---|---|---|
| cas limite | 131 | 63 % | brief implement |
| contrat mal lu | 37 | 18 % | fiche |
| affirmation fausse | 22 | 11 % | auto-vérification avant rendu |
| test cassé | 10 | 5 % | porte locale |
| test vide | 8 | 4 % | brief implement |

Contrôle : la mesure du 31-10 (86 passes, depuis le 30-10) donnait 64 % de cas limites ; celle-ci en donne 63 %, elle ne la contredit pas. Le bug de code passe de 51 % à 63 % des classées parce que le dénominateur n'est plus le même (fenêtre de 328 passes classées, sans revue exclues, contre 86 passes). Même réserve que le [30-10](bug-code-2026-10-30.md) : c'est la classification d'un modèle local, sans relecture à la main ; l'accord avec une relecture n'est pas calculé.

## 2. Les deux causes retenues

Règle (R1 de la fiche) : les deux sous-causes qui pèsent le plus de passes de bug de code, « autre » exclue, une égalité tranchée dans l'ordre de `SOUS_CAUSES` (`src/corrections.ts`), une seule cause s'il y a moins de deux sous-causes non vides.

Causes retenues : cas limite, contrat mal lu.

Part des deux causes : 81 % des passes de bug de code (168 sur 208) : cas limite 63 % (131), contrat mal lu 18 % (37). Pas d'égalité en deuxième place (37 contre 22). Les autres causes pèsent 19 % ; chaque ajout à la liste est un texte de plus à lire pour la session, d'où deux puces et pas davantage.

## 3. Le mécanisme posé

Emplacement : `templates/orchestrate/implement.md`, liste « Self-check before handing back », **une puce `[L543]` par cause retenue**, après les cinq puces existantes (inchangées). Chaque puce se fait sur le diff de la session avant de rendre et se **trace** dans le rapport :

- **cas limite** : la puce ne redonne pas la liste des entrées, c'est le point « edge cases » `[L447]` du bloc « Limits and rules » qui la demande et la fait jouer. Elle ajoute la trace : une ligne par entrée listée là, « entrée → attendu → obtenu », dans `resume`, et toute entrée non jouée sous `nonVerifie`.
- **contrat mal lu** : pour chaque règle Rn de la fiche (ou de l'énoncé du lot), citer le mot de la règle et la ligne de code qui la tient, relire l'énoncé après le code, et mettre sous `choix` toute différence.

Le texte des puces des autres sous-causes est fixé dans la fiche (`docs/specs/bug-code-autoverification-deux-causes/fiche.yaml`, R3) pour le cas où une mesure ultérieure les retiendrait ; il n'est pas dans le gabarit. Aucun autre gabarit (fix, spec, spec-back, review, probe) ni `src/testgate.ts` ne porte `[L543]`.

## 4. Protocole de mesure sur deux fenêtres

**La fenêtre suivante mesure L428, L447 et L497 ensemble, avec L543** : l'effet de L543 ne s'isole pas, il s'ajoute. Seules comptent les vagues **créées après** la mise en service du gabarit durci (le `npm run service` qui le met en service ; le brief d'une vague est celui de l'instantané pris à sa création, `<vague>/tool/`) : `--since <heure de la mise en service>`.

Pour chaque fenêtre de 7 jours (F1 puis F2), « Passes classées » = toutes les passes de la fenêtre moins celles « sans revue (tests rouges) » (comme la ligne « Avant » : 396 − 68 = 328) ; la part du bug de code est prise sur ce dénominateur :

```sh
cadence perf                                                   # part conforme du premier coup, lots à ≥ 2 passes
cadence corrections --classify --since <début de F> --until <fin de F>
```

| Fenêtre | Passes classées | bug de code | cas limite | contrat mal lu | Part conforme du premier coup | Lots à ≥ 2 passes |
|---|---|---|---|---|---|---|
| Avant : 27-10→03-11 | 328 | 208 (63 %) | 131 (63 % des bug de code) | 37 (18 % des bug de code) | 45 % (`cadence perf` du 03-11, fenêtre 28-10→03-11, précédente 63 %) | 32 % (`cadence perf`) |
| F1 (après) | à mesurer | à mesurer | à mesurer | à mesurer | à mesurer | à mesurer |
| F2 (après) | à mesurer | à mesurer | à mesurer | à mesurer | à mesurer | à mesurer |

Les fenêtres de `cadence perf` (28-10→03-11) et de `--classify` (27-10→03-11) diffèrent d'un jour : la ligne « Avant » le dit, F1 et F2 prennent les mêmes bornes pour les deux commandes.

Lecture : le mécanisme est utile si la part conforme du premier coup monte ET si la part des deux causes baisse, sans que les lots à ≥ 2 passes montent ; sinon le texte ou le maillon est à revoir. Une part qui baisse parce que les autres causes grossissent n'est pas un gain : classer d'abord, comparer ensuite. Cette règle de lecture est celle de l'auteur de la fiche (hypothèse R5) ; le critère du 30-10 portait sur la part des cas limites seule.
