# corrections

`cadence corrections [folder] [--classify [--model m]] [--cache file] [--cache-sous-causes file] [--sample n] [--until date] [--since date] [--json]` measures how often a wave
has to correct itself. From the folder a wave was launched from (default: the current one) it reads the journals
`<folder>/.cadence/runs/<wave>/<project>--<lot>.json` of **every project** and prints:

- the **lots with a correction**: of the lots that went through a successful write session, the share with at least one
  and at least two `fix` passes, per project and for visible versus non-visible lots (`61 %` and `29 %` of 263 lots in the 10-10 baseline);
- the **passes by cause**, in total, per project and **per visibility** (visible lots apart from the others, with the share of `spec-floue`, `regle-inventee` and `test-manquant` among each one's passes — the reference an evolution aimed at screens is compared to is that of the visible lots, not « all lots »: 16 % of 45 passes against 31 % overall in the 10-10 baseline). The cause of a pass is read from the findings of the review that
  precedes it, among: unclear spec or missing criterion (`spec-floue`), invented business rule (`regle-inventee`),
  architecture drift (`derive-architecture`), data / SQL (`donnees-sql`), code bug (`bug-code`), missing test
  (`test-manquant`), false review finding (`faux-constat`). One cause per pass: the root of what forced the fix. A pass with no review finding to read (triggered by red tests right after the write session) is counted apart as `sans-constat` and never sent to the model.

Without `--classify` the command calls no model: the passes not yet classified count as `non classé`. With `--classify`
each pass is classified by a **local model served by Ollama** (`OLLAMA_HOST`, default `http://localhost:11434`;
`--model`, default `mistral-small3.2:24b`; temperature 0, output constrained to the seven causes), off the Anthropic quota.
The classification is cached in `<folder>/.cadence/corrections.json` (or `--cache file`): a re-run classifies only the
new passes, and a pass the model could not answer stays out of the cache. `--sample n` prints `n` passes with findings spread
evenly over the sorted keys, with their findings and the model's cause, to be read by hand; a `manual` field written
beside a pass in the cache file (one of the seven causes, else the command refuses the file) overrides the model's cause in every table and gives the **agreement rate** of the model
on the reviewed sample. `--until date` (ISO, e.g. `2026-10-10T18:31Z`) reads only the waves created up to then (`created` in the wave's `wave.json`) and, in them, only the steps ended by then (`ended`), so that neither later waves nor a wave still running at that time change a published baseline; a wave or a step with no readable date is left out. `--since date` (ISO, same format) keeps only the lots of the waves **created after** that date (`created` in the wave's `wave.json`), **with all their passes**: a wave renders every brief from the copy of the tool frozen when it is created (`<wave>/tool/`), so the creation date of the wave, not the start of a lot, tells which brief the lot was given. A `--continue` wave created before a change of brief therefore does not give it to its lots, even those that start after the change (a difference of two unbounded runs is wrong as soon as a wave straddles the date); the exception is a wave resumed (`--resume`) without a snapshot (older than L61) or, with `--budget project:lot=+N`, from a snapshot older than L223: it runs with the current `dist/` and templates, so it does receive the new brief. A wave with no readable `created` is left out, by `--since` as by `--until`. `--since` is strict and `--until` inclusive, so a wave created exactly at the date is on the `--until` side only and the two sets never overlap; `--since` and `--until` can be combined (a window of creation dates). Together `--until d` and `--since d` split the waves, and they add up to the unbounded total only when `d` is set while no wave is running (between two sessions, as `npm run service` requires; `cadence orchestrate --status` shows none, **and** no wave created before `d` is still resumable: `--status` lists only the live waves, an interrupted or suspended one is not shown and `--resume` would replay passes after `d`; list them with `jq -r 'select(.status != "done") | "\(.id) \(.status) \(.created)"' <folder>/.cadence/runs/*/wave.json`, and finish each before setting `d` or never resume it): a wave created before `d` that ends a pass after `d` leaves that pass in neither (`--until` does not read it, so that a published baseline does not move), and a gap between the sum and the unbounded total means `d` fell inside a wave. `--json` prints the measure as data. The command reads the journals and writes nothing but the cache.
The first baseline is in [docs/mesures/corrections-2026-10-10.md](mesures/corrections-2026-10-10.md); `test/corrections-mesure.test.ts` replays its command on the journals and checks the document's results word for word (skipped when the journals are not there). The measure of the screen-sheet step against the visible lots of this baseline (L176: 8 lots with a sheet, verdict per row of the success table, token cost beside the passes avoided) is in [docs/mesures/etape-spec-2026-10-12.md](mesures/etape-spec-2026-10-12.md); the target of its third row is ≤ 8 %, half the 16 % reference. The measure of the back-end spec step against the non-visible lots (L190: 10 lots with a back-end sheet, passes by cause, token cost beside the passes avoided) is in [docs/mesures/etape-spec-back-2026-10-16.md](mesures/etape-spec-back-2026-10-16.md).
The reading of the « bug de code » passes of the 23–29-10 window, the block added to the `implement` brief against them (L428) and the protocol to measure its effect on two `cadence perf` windows are in [docs/mesures/bug-code-2026-10-29.md](mesures/bug-code-2026-10-29.md).

## Sub-causes of the « bug de code » passes (L447)

The cause `bug-code` alone is 69 % of the classified passes (74 of 107, 24→30-10) and does not say *which* bug. A pass whose retained cause (`manual`, else the model's) is `bug-code` and that has review findings is therefore also given **one sub-cause** from a closed list of seven: `cas-limite` (edge case not tested or not held), `test-casse` (an existing test broken by the change), `contrat-mal-lu` (contract, sheet or lot statement misread), `appelant-oublie` (a caller or another site to change was forgotten), `affirmation-fausse` (a document, comment or report that is false), `test-vide` (a test that cannot fail, or a behaviour with no test) and `autre`. A pass of another cause, or with no finding, is never sent to the model for this.

- `--classify` first classifies the causes as before, then asks the same local model for the sub-cause of each `bug-code` pass that has none (temperature 0, output constrained to the seven values, findings cut to 1500 characters). The answers are cached in `<folder>/.cadence/corrections-sous-causes.json` (or `--cache-sous-causes file`): an object `pass key → { sous, by, manual? }`. A failed answer (Ollama down, non-2xx status, value outside the list) leaves the pass out of the cache, counted « sans sous-cause » and taken again by the next `--classify`; `corrections.json` is not touched. A `manual` field (one of the seven values) beats the model in every table. An entry whose key is not a `bug-code` pass of the window (re-classified, cause changed by hand, key absent from the window) is ignored: neither counted, erased nor refused.
- An unreadable file (not a JSON object) or an unknown sub-cause makes the command refuse with exit code 1, naming the file (and the key), without printing or rewriting anything; an absent file reads as empty. Without `--classify` the file is read, never written.
- The report gains the section « Bug de code par sous-cause » (sub-cause, passes, share of the sub-classified passes, link) and a line « Maillon dominant ». `--json` gains the key `bugCode` — `{ classees, sansSousCause, parSousCause, maillon: { nom, raison } }`. With no `bug-code` pass in the window nothing is added: the text report and the JSON keys are those of before.

**The link.** Each sub-cause belongs to one link of the chain: `cas-limite` and `test-vide` to the `implement` brief, `affirmation-fausse` and `appelant-oublie` to the self-check before handing back, `test-casse` to the local gate, `contrat-mal-lu` to the sheet, `autre` to none. The **dominant link** is the one whose sub-causes weigh the most passes; it is named only when at least 10 passes are sub-classified and its passes are at least 40 % of them. With fewer, with a link under 40 %, or with two links tied at the top, the line says « aucun » and why. The two thresholds and the table are constants of `src/corrections.ts` (hypotheses: the link is recomputed at each read, nothing stores it). `cadence perf` prints the same count under « causes dominantes » for the current 7-day window — `bug de code (N passes sous-classées sur M) : 1. cas limite … · maillon dominant : …` — reading the cache without writing it: an absent file gives `sous-causes n/d · à classer : cadence corrections --classify`, an unreadable one a warning on stderr (`perf : <file> illisible, sous-causes n/d`) and no line, exit code 0 in both cases (`corrections.causes.current.bugCode` in `--json`). Over 7 days the 10-pass threshold is often not reached: « aucun » is then the usual answer, not an error.
